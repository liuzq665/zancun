# 1. 项目概述

## 1.1 课题背景

宿舍是大学生学习与生活的主要场所，宿舍管理水平直接影响学生的日常体验与学校后勤的服务质量。当前多数高校的宿舍管理仍处于半人工状态：

- **信息载体落后**：住宿分配与调整依赖纸质台账和 Excel，信息更新滞后、版本混乱；
- **流程不可追溯**：卫生检查、报修、留宿等高频事务依靠口头传达或微信群接龙，缺乏统一的流程记录，处理结果难以追溯；
- **三方信息不对称**：宿管员、学生、学校管理部门之间信息不通，入住率、空床位等数据需人工盘点，既耗时又容易出错；
- **通知触达率低**：停水停电等通知仅张贴于宿舍楼下公告处，未及时看到的学生措手不及，宿管被反复询问。

调查归纳出当前宿舍管理的三类典型人工流程：

| 流程 | 现状链路 | 主要问题 |
| --- | --- | --- |
| 调宿 | 学生到宿管处领纸质申请表 → 填写原因 → 辅导员签字 → 交回宿管 → 宿管查床位 → 人工安排 → 通知学生 → 更新纸质台账 | 链路长、依赖签字、状态不透明 |
| 报修 | 学生通过微信群/电话/口头报修 → 宿管记录 → 联系维修人员 → 上门 → 口头反馈 | 无统一工单记录、进度不透明、责任难界定 |
| 查寝与统计 | 宿管人工查寝、纸质登记 | 数据分散、难以汇总分析、无决策支撑 |

## 1.2 系统目标

针对上述现状，本系统拟解决的核心问题是：**建立统一的宿舍数据台账，并将高频事务线上化、流程化**。总体目标概括为三个"化"：

| 目标 | 内涵 | 对应能力 |
| --- | --- | --- |
| **流程线上化** | 报修、留宿、账号管理全流程线上闭环 | 申请 → 受理 → 处理 → 反馈 → 归档 全程留痕 |
| **通知精准化** | 站内消息精准触达，信息主动找人 | 按角色/楼栋/个人精准推送，替代楼道张贴 |
| **管理数据化** | 统计报表沉淀数据，支撑管理决策 | 入住率、报修完成率、超时率、满意度等指标 |

功能层面的交付边界：

1. 建立 **宿舍楼 — 房间 — 床位** 三级数据模型，实现住宿信息集中管理与实时查询；
2. 实现学生入住信息的线上办理与历史追溯，保证数据在各环节实时一致；
3. 实现 **报修** 与 **假期留宿** 两类核心审批流程的完整闭环；
4. 为管理员自动生成入住率、报修完成率、留宿人数等统计报表，替代人工盘点；
5. 按 **管理员 — 宿管员 — 维修工 — 学生** 四类角色划分功能与数据权限，解决信息不对称问题。

## 1.3 角色与模块总览

### 1.3.1 角色定义

> **注意**：拟题报告与路演 PPT 描述为"3 个角色"（学生 / 宿管 / 系统管理员），但《用户故事地图》明确列出了 **维修工** 的独立角色与功能集。报修流程中维修工是接单、拒单、延期、完工的操作主体，且拥有独立的通知、工单记录与评价查看视图。**本设计采用 4 角色模型**，详见 [8.7 需求基线冲突与裁决建议](#87-需求基线冲突与裁决建议)。

| 角色 | 编码 | 职责概述 | 数据可见范围 |
| --- | --- | --- | --- |
| 学生 | `STUDENT` | 查看住宿信息、提交报修/留宿申请、确认维修、评价 | 仅本人 |
| 宿管员 | `DORM_MANAGER` | 审核工单与留宿申请、派单、管理管辖楼栋 | 所辖楼栋 |
| 维修工 | `REPAIRER` | 接收/拒绝工单、现场维修、上传结果 | 本人被派工单 |
| 系统管理员 | `ADMIN` | 账号与资源管理、规则配置、全校数据统览 | 全校 |

### 1.3.2 功能模块总览

系统划分为 **5 个业务模块 + 1 个系统通用模块**：

| # | 模块 | 核心内容 | 主要角色 |
| --- | --- | --- | --- |
| 1 | 账号管理 | 登录、改密、个人信息维护、账号增删改查、启停用、重置密码、分配负责楼栋 | 全部 / 管理员 |
| 2 | 消息通知 | 站内消息收发、定时群发、业务事件通知、已读未读 | 全部 |
| 3 | 入宿管理 | 楼栋/房间/床位维护、床位分配、入住信息查询与历史追溯、批量导入导出 | 管理员 / 宿管 / 学生 |
| 4 | 报修管理 | 工单提交、审核、自动/手动派单、接单/拒单、维修延期、完工确认、复修、评价、归档 | 全部 |
| 5 | 假期留宿 | 开放时段配置、截止时间设置、申请提交、锁定、审核、归档、名单统计 | 管理员 / 宿管 / 学生 |
| 6 | 系统通用 | 操作日志查看、数据备份 | 管理员 |

## 1.4 版本迭代规划

采用**用户故事地图**驱动、三阶段增量交付的迭代路径：**V1 求闭环、V2 求效率、V3 求智能**。

| 阶段 | 定位 | 交付重点 | 交付判据 |
| --- | --- | --- | --- |
| **V1** MVP 基础版 | 跑通核心业务闭环 | 账号与权限体系、宿舍资源模型、报修全流程（含派单/接单/完工/确认/评价）、站内消息、基础数据配置 | 彻底告别线下表格与纸质单据，报修实现端到端闭环 |
| **V2** 迭代完善 | 数据沉淀 × 统计分析 × 批量操作 | 入住/报修/留宿历史追溯、定时通知、批量导入导出、全校统计报表、操作日志、数据备份 | 数据沉淀下来，为管理决策提供支撑 |
| **V3** 智能化升级 | 引入新技术提升智能化 | 学生端智能客服、维修工单自动派发、可视化数据大屏、小程序/H5 移动端 | 从"能用"走向"好用"，一屏统览、心中有数 |

## 2.2 后端选型论证

### 2.2.1 Spring Boot + MyBatis + MySQL

拟题报告已明确采用该组合，本设计沿用，理由如下：

| 维度 | 论证 |
| --- | --- |
| **与课程契合** | 团队已修 JavaWeb / 数据库课程，Spring Boot 是教学主线，技术风险最低 |
| **B/S 架构适配** | 系统本质是多角色浏览器访问的信息管理系统，B/S 是天然选择 |
| **复杂度可控** | 业务以增删改查 + 状态流转为主，无需微服务化；单体应用足以支撑千级学生、百级宿舍的数据规模 |
| **生态成熟** | Spring 生态在权限、校验、事务、定时任务、文件上传等方面均有开箱即用的解决方案 |
| **CodeArts 兼容** | Maven 项目可直接被 CodeArts 编译构建流水线识别，无需改造 |

**为什么选择 MyBatis-Plus 而非纯 MyBatis 或 JPA：**

- 相比纯 MyBatis：MyBatis-Plus 提供 `BaseMapper` 通用 CRUD、条件构造器、分页插件、逻辑删除、自动填充（`create_time` / `update_time` / `create_by`），可减少约 60% 的样板 SQL；
- 相比 JPA：本系统存在大量**多表统计查询**（入住率、报修完成率、超时率），JPA 的 ORM 自动关联在这种场景下易产生 N+1 查询，SQL 可控性差；MyBatis 的 XML 手写 SQL 更利于性能调优与统计口径统一；
- 采用 **MyBatis-Plus 通用方法处理单表 CRUD + XML 手写复杂查询** 的混合模式。

### 2.2.2 Spring Security + JWT

报修与留宿流程涉及 **4 类角色的细粒度数据权限**（宿管只能看所辖楼栋、维修工只能看自己被派的工单），这是拟题报告列出的难点之一。

| 方案 | 取舍 |
| --- | --- |
| Session + Cookie | 跨域配置繁琐，前后端分离下需额外处理 CORS 与 CSRF，且不利于 V3 小程序复用 |
| **JWT（选定）** | 无状态、天然支持前后端分离与多端复用（Web + V3 小程序共用同一套 Token 机制）；角色与数据范围写入 Claim，网关层即可完成粗粒度鉴权 |

**数据范围隔离**通过自定义注解 `@DataScope(scope = BUILDING)` + AOP 切面实现：切面在 DAO 查询前，向 SQL 自动追加 `building_id IN (当前用户所辖楼栋)` 条件，从机制上杜绝越权查询，而非依赖每个 Service 手工拼条件。

### 2.2.3 Redis 的定位（可选组件）

Redis **不是 V1 的强制依赖**。V1 可用本地 `Caffeine` 缓存 + 数据库乐观锁满足需求。引入 Redis 的场景与收益：

| 场景 | 无 Redis 方案 | 有 Redis 方案 |
| --- | --- | --- |
| 并发锁定（学生同时提交同一床位） | 数据库唯一索引 + 乐观锁 | 分布式锁，减少无效重试 |
| 登录 Token 黑名单（主动登出） | 需查库 | SET 结构，O(1) |
| 超时工单扫描 | 定时任务全表扫描 | ZSet 延迟队列，精确触发 |

**建议**：V1 采用 Caffeine + 数据库乐观锁；若 V2 阶段部署环境已具备 Redis，则迁移至 Redis 方案。本设计的状态机与并发控制方案**不依赖 Redis 即可正确工作**。

### 2.4.2 为什么引入 Flyway

数据库变更是课设项目最常见的协作冲突源——多人各自手工改库导致环境不一致。Flyway 以版本化 SQL 脚本管理 Schema：

- 所有 DDL 存放于 `db/migration/V{n}__{desc}.sql`，随代码入库；
- 应用启动时自动校验并执行未应用的迁移；
- 新成员加入只需拉起应用即可获得完整数据库结构，无需人工导入。

## 3.2 分层职责

| 层 | 职责 | 禁止事项 |
| --- | --- | --- |
| **Controller** | 接收请求、参数校验（`@Valid`）、权限注解、调用 Service、封装响应 | ✗ 不含业务逻辑；✗ 不直接调用 Mapper |
| **Service** | 业务编排、事务边界（`@Transactional`）、状态机流转、数据范围过滤 | ✗ 不返回 Entity 给 Controller；✗ 不拼接 HTTP 语义 |
| **Mapper** | 数据访问，单表走 MyBatis-Plus 通用方法，多表统计走 XML | ✗ 不含业务判断 |
| **Entity** | 与数据库表一一对应 | ✗ 不直接对外暴露 |
| **DTO** | 入参对象，携带校验注解 | — |
| **VO** | 出参对象，按前端视图裁剪字段 | — |
| **Convert** | MapStruct 在 Entity / DTO / VO 间转换 | ✗ 不含业务逻辑 |

**为什么强制 Entity 不对外暴露**：Entity 携带 `password`、`is_deleted`、内部状态计数等字段。直接序列化返回会导致**密码哈希泄露**与**前端过度依赖内部结构**（表结构变更即破坏前端）。所有出参统一走 VO。

## 3.3 权限模型

### 3.3.1 三层权限

| 层次 | 载体 | 作用 |
| --- | --- | --- |
| **认证** | JWT Token | 校验身份有效性，解析 `userId` / `role` |
| **功能权限** | `@PreAuthorize("hasRole('ADMIN')")` | 控制接口能否访问 |
| **数据权限** | `@DataScope(scope = BUILDING)` | 控制能访问**哪些数据行** |
| **前端权限** | 路由 `meta.roles` + `v-permission` 指令 | 控制菜单与按钮可见性 |

### 3.3.2 数据范围规则

| 角色 | `DataScope` | 生效条件 |
| --- | --- | --- |
| `ADMIN` | `ALL` | 不追加过滤条件 |
| `DORM_MANAGER` | `BUILDING` | 追加 `building_id IN (SELECT building_id FROM dorm_building WHERE manager_id = #{userId})` |
| `REPAIRER` | `SELF` | 追加 `current_worker_id = #{userId}` |
| `STUDENT` | `SELF` | 追加 `student_id = #{userId}` |

**设计要点**：数据范围过滤在 **Mapper 层统一注入**，而非在 Service 逐个方法手写 `if (role == DORM_MANAGER)`。原因：手工判断极易遗漏，一处遗漏即造成越权数据泄露，且随接口增长风险持续放大；AOP 注入是"默认安全"的——新增查询接口自动获得正确的数据范围。

### 3.3.3 JWT 载荷设计

```json
{
  "sub": "1024",
  "role": "DORM_MANAGER",
  "realName": "张宿管",
  "iat": 1758787200,
  "exp": 1758873600,
  "jti": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

| 字段 | 说明 |
| --- | --- |
| `sub` | 用户 ID |
| `role` | 角色编码，用于 `hasRole` 判断 |
| `jti` | Token 唯一 ID，用于主动登出时的黑名单 |
| `exp` | 过期时间，默认 24 小时 |

**载荷中不存放敏感信息**（密码、手机号等）。JWT 仅 Base64 编码而非加密，任何持有者可解码读取内容。

## 3.4 统一响应与异常

### 3.4.1 响应结构

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "timestamp": 1758787200000
}
```

### 3.4.2 状态码规范

| `code` | 含义 | HTTP 状态 |
| --- | --- | --- |
| `0` | 成功 | 200 |
| `400xx` | 参数校验失败 | 400 |
| `40100` | 未登录 / Token 失效 | 401 |
| `40300` | 无权限访问 | 403 |
| `40400` | 资源不存在 | 404 |
| `409xx` | 状态冲突 / 并发冲突 | 409 |
| `500xx` | 系统内部错误 | 500 |

**为什么 HTTP 状态与业务 code 并存**：HTTP 状态用于表达**协议层语义**（网关、浏览器、监控系统依赖它做重试与告警）；业务 code 用于表达**细分的业务失败原因**（如"该工单已被其他维修工接单"）。只用一个会导致语义丢失。

### 3.4.3 异常体系

```
BusinessException (自定义业务异常, 携带 code + message)
  ├── ParamException        参数校验失败
  ├── AuthException         认证失败
  ├── PermissionException   权限不足
  ├── StateConflictException 状态机非法流转
  └── ConcurrencyException  并发冲突 (乐观锁失败)

由 @RestControllerAdvice 全局捕获:
  ├── BusinessException        → 按携带的 code 返回
  ├── MethodArgumentNotValidException → 40001
  ├── AccessDeniedException    → 40300
  ├── Exception (兜底)         → 50000 + 记录完整堆栈
```

**兜底异常处理必须记录完整堆栈但不向前端泄露堆栈内容**——堆栈包含类名、路径、SQL 片段，属于攻击者可利用的信息。

# 5. 核心状态机设计

状态机是本系统区别于普通 CRUD 课设的核心设计。拟题报告将其列为难点与创新点：*"状态机驱动业务，将床位状态、调宿申请状态、报修工单状态通过状态机精细化管理，杜绝逻辑漏洞"*。

## 5.1 报修工单状态机

### 5.1.1 状态定义

| 状态码 | 状态名 | 进入条件 | 可操作角色与动作 |
| --- | --- | --- | --- |
| `DRAFT` | 草稿 | 学生保存未提交 | 学生：编辑 / 删除 / 提交 |
| `PENDING_REVIEW` | 待审核 | 学生提交 | 学生：撤销；宿管：审核通过 / 驳回 |
| `REJECTED` | 已驳回 | 宿管审核不通过 | 学生：重新编辑并提交 / 删除 |
| `PENDING_ASSIGN` | 待派单 | 审核通过，或工单回流 | 系统：自动派单；宿管：手动强制派单 |
| `ACCEPTED` | 已接单 | 维修工确认接单，或强制派单自动接单 | 维修工：延期 / 完工 |
| `DELAYED` | 维修延期 | 现场无法一次性完成 | 维修工：再次延期 / 完工 |
| `REPAIRED` | 已维修 | 维修工填写结果并上传完工照片 | 学生：确认（评价） / 申请复修 |
| `CONFIRMED` | 已确认 | 学生确认，或超时自动确认 | 系统：归档 |
| `ARCHIVED` | 已归档 | 归档完成 | 只读 |

### 5.1.3 流转规则表

| 当前状态 | 触发动作 | 目标状态 | 触发角色 | 附加动作 |
| --- | --- | --- | --- | --- |
| `DRAFT` | 提交 | `PENDING_REVIEW` | 学生 | 生成工单号、记录 `submit_time`、推送消息给宿管 |
| `DRAFT` | 删除 | — | 学生 | 逻辑删除 |
| `PENDING_REVIEW` | 撤销 | `DRAFT` | 学生 | — |
| `PENDING_REVIEW` | 审核通过 | `PENDING_ASSIGN` | 宿管 | 记录 `review_by` / `review_time`；紧急工单设 `priority=URGENT`；推送消息给学生 |
| `PENDING_REVIEW` | 审核驳回 | `REJECTED` | 宿管 | 必填 `reject_reason`；推送消息给学生 |
| `REJECTED` | 重新提交 | `PENDING_REVIEW` | 学生 | 清空上一轮 `reject_reason` |
| `PENDING_ASSIGN` | 自动派单 | `PENDING_ASSIGN` | 系统 | 创建 `PENDING` 状态的派单记录，`current_worker_id` 赋值 |
| `PENDING_ASSIGN` | 手动强制派单 | `ACCEPTED` | 宿管 | 创建派单记录并**直接置为已接单**；`accept_type=FORCE`；记录 `accept_time` |
| `PENDING_ASSIGN` | 接单 | `ACCEPTED` | 维修工 | 派单记录置 `ACCEPTED`；记录 `accept_time`；**启动施工超时计时** |
| `PENDING_ASSIGN` | 拒单 | `PENDING_ASSIGN` | 维修工 | 派单记录置 `REJECTED`；`reject_count++`；写拒单记录；判断是否达 2 次 |
| `PENDING_ASSIGN` | 接单超时 | `PENDING_ASSIGN` | 系统 | 派单记录置 `TIMEOUT`；`timeout_accept_count++`；写超时未处理工单记录；判断是否达 2 次 |
| `ACCEPTED` | 申请延期 | `DELAYED` | 维修工 | 必填 `delay_reason` / `delay_images` / `delay_expect_time` |
| `ACCEPTED` | 完工 | `REPAIRED` | 维修工 | 必填 `repair_result` / `finish_images`；记录 `finish_time`；推送消息给学生 |
| `ACCEPTED` / `DELAYED` | 施工超时（超时未修好） | `PENDING_ASSIGN` | 系统 | 标记 `is_abnormal=1`；写超时未修好工单记录；**单次即标记异常，直接进手动派单池** |
| `DELAYED` | 再次延期 | `DELAYED` | 维修工 | 更新延期信息 |
| `DELAYED` | 完工 | `REPAIRED` | 维修工 | 同 `ACCEPTED` 完工 |
| `REPAIRED` | 学生确认 | `CONFIRMED` | 学生 | 记录 `confirm_time` / `confirm_type=MANUAL`；开放评价入口 |
| `REPAIRED` | 超时自动确认 | `CONFIRMED` | 系统 | `confirm_type=AUTO`（默认完工后 7 天） |
| `REPAIRED` | 申请复修 | `PENDING_ASSIGN` | 学生 | 标记 `is_rework=1`；写重修记录；推送消息给宿管手动派单 |
| `CONFIRMED` | 归档 | `ARCHIVED` | 系统 / 宿管 | 记录 `archive_time` |

### 5.1.4 异常工单与派单池规则

#### 5.1.4.1 记录类型（每次发生均需记录）

| 记录类型 | 触发时机 | 写入表 |
| --- | --- | --- |
| **拒单记录** | 维修工拒单 | `repair_worker_record` (`record_type = REJECT`) |
| **超时未处理工单记录** | 派单后超过2小时未接单 | `repair_worker_record` (`record_type = TIMEOUT_ACCEPT`) |
| **超时未修好工单记录** | 接单后施工超时（常规24h/紧急6h） | `repair_worker_record` (`record_type = TIMEOUT_HANDLE`) |
| **延期工单记录** | 维修工申请延期 | `repair_worker_record` (`record_type = DELAY`) |
| **重修工单记录** | 学生申请复修 | `repair_worker_record` (`record_type = REWORK`) |

#### 5.1.4.2 异常工单判定规则

`is_abnormal` 为**标记位而非状态**。触发条件：

| 触发条件 | 次数门槛 | 触发时机 |
| --- | --- | --- |
| 超时未处理工单 | **> 2次**（即第3次触发） | 接单超时扫描时，`timeout_accept_count > 2` |
| 拒单 | **> 2次**（即第3次触发） | 拒单时，`reject_count > 2` |
| 超时未修好工单 | **≥ 1次**（单次即触发） | 施工超时扫描时 |

#### 5.1.4.3 派单池归属

工单的派单池归属由以下规则决定（按优先级从高到低）：

| 优先级 | 工单类型 | 派单池 | 说明 |
| --- | --- | --- | --- |
| 1 | 紧急工单（`priority = URGENT`） | **始终手动派单池** | 不参与自动派单，强制走手动派单 |
| 2 | 重修工单（`is_rework = 1`） | **始终手动派单池** | 需宿管人工指定维修工 |
| 3 | 异常工单（`is_abnormal = 1`） | **手动派单池** | 被异常触发后不再参与自动派单 |
| 4 | 普通工单（`is_abnormal = 0` 且非紧急非重修） | **自动派单池** | 系统按负载均衡自动派单 |

**派单池判定时机**：
- 紧急工单：创建时即进入手动派单池
- 重修工单：学生申请复修时进入手动派单池
- 异常工单：满足异常触发条件后（拒单>2 或 超时未处理工单>2 或 超时未修好1次）进入手动派单池
- 普通工单：正常参与自动派单，回流后若未触发异常条件仍回自动派单池

**为什么用标记而非独立状态**：若增加 `ABNORMAL` 状态，则"异常工单被派单后"需再定义从 `ABNORMAL` 到 `ACCEPTED` 的转移，且异常工单仍需经历待派单→已接单→已维修的完整链路，状态会重复。用标记位可保持状态机简洁，同时通过 `is_abnormal=1` 过滤手动派单池。

> **术语说明**（根据报修业务流程.drawio）：
> - **超时未处理工单**：派单后超2小时未接单（既没接单也没拒单）
> - **超时未修好工单**：已接单后超时限未修好（施工超时）

## 5.2 派单记录状态机

一张工单可有多条派单记录（每次回流产生新记录），因此派单状态独立于工单状态。

| 状态码 | 状态名 | 说明 |
| --- | --- | --- |
| `PENDING` | 待接单 | 已派单，等待维修工响应 |
| `ACCEPTED` | 已接单 | 维修工确认接单 |
| `REJECTED` | 已拒单 | 维修工拒单，含 `reject_reason` |
| `TIMEOUT` | 超时未接 | 超过接单时限未响应 |
| `CANCELLED` | 已作废 | 工单已由其他派单完成 |

**约束**：同一工单在同一时刻**最多只有一条** `PENDING` 或 `ACCEPTED` 状态的派单记录。通过数据库部分唯一索引保证：

```sql
-- MySQL 8.0 不支持部分索引，改用触发器或在应用层校验
-- 应用层：派单前 SELECT ... WHERE order_id = ? AND status IN ('PENDING','ACCEPTED') FOR UPDATE
```

## 5.3 留宿申请状态机

### 5.3.1 状态定义

| 状态码 | 状态名 | 进入条件 |
| --- | --- | --- |
| `DRAFT` | 草稿 | 学生保存未提交 |
| `PENDING_REVIEW` | 待审核 | 学生提交 |
| `REJECTED` | 已驳回 | 宿管统一驳回 |
| `APPROVED` | 审核通过 | 宿管审核通过 |
| `ARCHIVED` | 已归档 | 留宿时段结束，系统自动归档 |

### 5.3.2 状态流转图

```
   ┌──────────┐  学生提交   ┌────────────────┐
   │  DRAFT   ├────────────►│ PENDING_REVIEW │
   └──────────┘             └───────┬────────┘
        ▲                           │
        │                   宿管锁定 │（置 is_locked=1，
        │                           │  状态不变，仍为待审核，
        │                           │  截止时间到后执行）
        │                           ▼
        │                  ┌─────────────────┐
        │                  │ 锁定后统一审核    │
        │                  └────┬───────┬────┘
        │              审核通过 │       │ 统一驳回
        │                       ▼       ▼
        │             ┌──────────┐  ┌──────────┐
        │             │ APPROVED │  │ REJECTED │
        │             └────┬─────┘  └──────────┘
        │                  │
        │        留宿时段结束│ 系统自动归档
        │                  ▼
        │            ┌──────────┐
        └────────────┤ ARCHIVED │
       (归档后如允许  └──────────┘
        再次申请)
```

**截止时间说明**：宿管设置的 `apply_deadline` 控制学生**编辑提交**的截止时间，截止后宿管执行锁定冻结编辑；系统管理员设置的 `stay_start_date` / `stay_end_date` 控制学生可**填写的留宿日期范围**，两者是不同维度的约束。

### 5.3.3 流转规则表

留宿申请存在**两层截止时间**，含义不同：

| 层次 | 控制者 | 字段 | 控制内容 |
| --- | --- | --- | --- |
| **申请窗口** | 系统管理员 | `stay_batch.open_start_time` / `open_end_time` | 批次维度的申请开放时段，超出则整个批次不可申请 |
| **编辑截止** | 宿管 | `stay_batch_building.apply_deadline` | 该楼栋学生可编辑（保存/修改/提交/撤销）的截止时间，截止后宿管执行锁定冻结编辑 |

> **语义澄清**：宿管设置的截止时间到后，宿管执行锁定操作（`is_locked=1`），学生**无法再编辑**；系统管理员设置的留宿时间（`stay_start_date` / `stay_end_date`）用于**限定学生可填写的留宿日期范围**，学生填写的留宿开始/结束日期必须落在管理员给定的假期留宿范围内。

| 当前状态 | 触发动作 | 目标状态 | 触发角色 | 约束 |
| --- | --- | --- | --- | --- |
| `DRAFT` | 提交 | `PENDING_REVIEW` | 学生 | 必须早于 `apply_deadline` 且 `is_locked = 0` |
| `DRAFT` | 删除 | — | 学生 | `is_locked = 0` |
| `PENDING_REVIEW` | 撤销 | `DRAFT` | 学生 | `is_locked = 0` |
| `PENDING_REVIEW` | 修改 | `PENDING_REVIEW` | 学生 | `is_locked = 0` |
| `PENDING_REVIEW` | **锁定** | `PENDING_REVIEW` | 宿管 | 置 `is_locked = 1`；**状态不变**；此后学生所有写操作被拒 |
| `PENDING_REVIEW` | 审核通过 | `APPROVED` | 宿管 | 记录 `review_by` / `review_time` |
| `PENDING_REVIEW` | 统一驳回 | `REJECTED` | 宿管 | **批量操作**：等全部申请审核完毕后再统一驳回 |
| `APPROVED` | 归档 | `ARCHIVED` | 系统 | 留宿结束日期到达后自动触发 |

**关键设计点 — 锁定与状态解耦**：根据 `假期留宿业务流程.docx`：
> "学生提交申请后，申请状态变为待审核。宿管执行锁定操作，锁定之后学生不能再对留宿申请进行修改。"

**锁定仅冻结编辑权限，不改变申请状态**。学生提交申请后状态立即变为"待审核"，宿管锁定后状态保持为"待审核"，只是置 `is_locked=1` 禁止学生继续编辑。因此用 `is_locked` 布尔字段而非状态枚举值表达。

**统一驳回的批量语义**：审核不通过时，宿管需等待全部申请审核完毕后统一驳回。这要求：
1. 驳回操作支持**批量提交**（一次请求携带多个 `applicationId`）；
2. 驳回时校验该批次下**不存在仍处于待审核的申请**，否则拒绝操作并提示剩余数量。

## 5.4 定时器与超时判定

本系统存在 **3 类共 5 个计时器**，均通过 `@Scheduled` 定时任务扫描实现。

> **术语说明**（根据报修业务流程.drawio）：
> - **超时未接单/超时未处理工单**：派单后超过时限未接单（既没接单也没拒单）
> - **超时未修好**：已接单后超过时限未修好（接单超时是施工超时的前置阶段）

| # | 计时器 | 起算点 | 默认阈值 | 扫描频率 | 触发动作 |
| --- | --- | --- | --- | --- | --- |
| 1 | **接单超时**（超时未处理工单） | 派单时刻 `dispatch_time` | 2 小时 | 每 5 分钟 | 派单记录置 `TIMEOUT`；`timeout_accept_count++`；写超时未处理工单记录；判断回流 |
| 2 | **施工超时**（超时未修好工单/常规） | 接单时刻 `accept_time` | 24 小时 | 每 10 分钟 | 标记异常；写超时未修好工单记录；回流手动派单池 |
| 3 | **施工超时**（超时未修好工单/紧急） | 接单时刻 `accept_time` | 6 小时 | 每 10 分钟 | 同上 |
| 4 | **学生确认超时** | 完工时刻 `finish_time` | 7 天 | 每日 01:00 | 自动确认 `confirm_type=AUTO` |
| 5 | **留宿自动归档** | 留宿结束日期 `stay_end_date` | — | 每日 02:00 | 申请置 `ARCHIVED` |

### 5.4.1 阈值配置化

阈值**不硬编码**，存于 `sys_config` 表，管理员可在 `报修管理 → 规则设置` 中调整：

| 配置键 | 默认值 | 含义 | 依据 |
| --- | --- | --- | --- |
| `repair.accept.timeout.hours` | 2 | **接单超时**：派单后超过此时限未接单，计入超时未处理工单记录 | 报修业务流程.drawio |
| `repair.arrive.timeout.normal.hours` | 24 | **施工超时（常规）**：接单后超过此时限未修好，超时未修好工单，标记异常 | 报修业务流程.drawio |
| `repair.arrive.timeout.urgent.hours` | 6 | **施工超时（紧急）**：接单后超过此时限未修好，超时未修好工单，标记异常 | 报修业务流程.drawio |
| `repair.confirm.auto.days` | 7 | 学生确认超时自动确认（天） | 待确认事项Q6 |
| `repair.abnormal.threshold` | 2 | 异常工单判定次数门槛（超时未处理工单超过2次 或 拒单超过2次，各自独立） | 报修业务流程.drawio |

**超时类型说明**（根据报修业务流程.drawio）：

| 超时类型 | 别名 | 场景 | 阈值 | 异常判定 |
| --- | --- | --- | --- | --- |
| **接单超时** | 超时未处理工单 | 派单后超2小时未接单（既没接单也没拒单） | 2小时 | `timeout_accept_count > 2` → 异常（第3次触发） |
| **施工超时** | 超时未修好工单 | 已接单后超时限未修好 | 常规24h / 紧急6h | **单次即标记异常**，无次数门槛 |

**为什么配置化**：拟题报告的功能目标明确"支持管理员设置工单核心规则如超时工单判定标准等规则"。硬编码阈值会使该功能无法实现，且不同学校、不同学期的管理尺度不同，配置化是刚性需求。

### 5.4.2 定时任务实现要点

```java
@Component
@RequiredArgsConstructor
public class RepairTimeoutTask {

    private final RepairDispatchMapper dispatchMapper;
    private final RepairOrderService repairOrderService;
    private final SysConfigService configService;

    /** 接单超时扫描：每 5 分钟 */
    @Scheduled(cron = "0 */5 * * * ?")
    public void scanAcceptTimeout() {
        int hours = configService.getInt("repair.accept.timeout.hours", 2);
        LocalDateTime deadline = LocalDateTime.now().minusHours(hours);
        // 只扫 PENDING 状态且派单时间早于 deadline 的记录
        List<RepairDispatch> list =
            dispatchMapper.selectTimeoutPending(deadline);
        for (RepairDispatch d : list) {
            repairOrderService.handleAcceptTimeout(d.getId());
        }
    }

    /** 施工超时扫描：每 10 分钟 */
    @Scheduled(cron = "0 */10 * * * ?")
    public void scanArriveTimeout() {
        // 分别按常规/紧急阈值扫描 ACCEPTED 和 DELAYED 状态的工单
        ...
    }
}
```

**并发安全**：定时任务在多实例部署时会重复执行。V1 为单实例部署，无此问题；若 V2 扩展为多实例，需引入分布式锁（Redis `SETNX`）或 ShedLock。**本设计在 V1 明确约束为单实例部署**（见 [8.6 技术约束](#86-技术约束)）。

**批量处理与事务边界**：单个工单的超时处理是独立事务。若循环中一个工单处理失败，不应影响其他工单。因此 `handleAcceptTimeout` 标注 `@Transactional(propagation = REQUIRES_NEW)`，并在循环中捕获异常记录日志而非中断整批。

## 5.5 自动派单算法

### 5.5.1 需求约束

报修流程前置约束给出了两条对算法有决定性影响的信息：

1. *"总维修人员数量超过 2，所以可能存在某个工种只有一个维修人员的情况"* —— 候选集可能极小，算法必须能处理**候选集为空**与**候选集仅 1 人**的边界；
2. *"宿管和系统会按照维修类型的工种和工单数量分配维修人员"* —— 排序维度为**工种匹配** + **工单负载**。

### 5.5.2 算法流程

```
输入：工单 order (含 work_type_id, building_id)
输出：选中的维修工 ID，或派单失败原因

Step 1  构建候选集
        SELECT w.id
        FROM   sys_user w
        JOIN   repair_worker_scope s ON s.worker_id = w.id
        WHERE  w.role = 'REPAIRER'
          AND  w.status = 1                      -- 账号启用
          AND  s.work_type_id = #{workTypeId}    -- 工种匹配

Step 2  排除本轮已拒绝过该工单的维修工
        AND w.id NOT IN (SELECT worker_id FROM repair_dispatch
                         WHERE order_id = #{orderId}
                           AND status IN ('REJECTED','TIMEOUT'))

Step 3  统计负载
        对候选集中的每人，统计其当前"在手工单数"：
        SELECT worker_id, COUNT(*) AS load
        FROM   repair_order
        WHERE  current_worker_id IN (候选集)
          AND  status IN ('ACCEPTED','DELAYED')   -- 已接单/延期视为在手工
        GROUP BY worker_id

Step 4  排序取首位
        ORDER BY load ASC,                      -- ① 负载最少优先
                 last_dispatch_time ASC NULLS FIRST  -- ② 最久未被派单优先
        LIMIT 1

Step 5  结果判定
        候选集为空  → 返回失败："该工种暂无可用维修人员，请手动派单"
        选中成功    → 创建 repair_dispatch 记录（status=PENDING）
```

### 5.5.3 边界处理

> **派单池归属规则见 [5.1.4.3 派单池归属](#5143-派单池归属)**

| 边界 | 处理 |
| --- | --- |
| 候选集为空（工种无人或全部拒过） | 工单**保持** `PENDING_ASSIGN`，标记 `is_abnormal=1` 进入手动派单池，推送消息给宿管；**不阻塞**后续扫描 |
| 候选集仅 1 人且其负载很高 | 仍派给他（工种唯一，无替代）；若他拒单/超时，按正常流程回流 |
| 全部候选人都在休假/停用 | 同"候选集为空"处理 |
| 并发派单（两个工单同时选中同一人） | 派单操作在数据库事务内执行，并对候选人的负载统计加 `FOR UPDATE`；或接受轻微不均衡（下一步扫描会自然校正） |

**为什么第二个排序键是 `last_dispatch_time` 而非"距上次完成时间"**：在候选人数少（可能只有 1–2 人）时，负载值会频繁相同。若第二排序键缺失或使用不稳定字段，会导致**总是派给同一人**。引入 `last_dispatch_time ASC` 保证轮转公平。

### 5.5.4 V3 策略可插拔设计

V3 规划"自动给维修派单"。为便于引入更复杂的策略（如基于地理位置、技能等级、历史评分的加权派单），V1 即抽象策略接口：

```java
public interface DispatchStrategy {
    /** 策略编码，如 "LOAD_BALANCE"、"WEIGHTED" */
    String code();
    /** 从候选集中选出目标维修工；无法选出时返回 Optional.empty() */
    Optional<Long> select(RepairOrder order, List<CandidateWorker> candidates);
}
```

V1 提供 `LoadBalanceDispatchStrategy` 实现；V3 新增策略只需实现接口并注册为 Bean，无需改动派单主流程。

# 6. 数据库设计

## 6.1 设计约定

| 约定项 | 规范 |
| --- | --- |
| 引擎 | InnoDB |
| 字符集 | `utf8mb4` / `utf8mb4_0900_ai_ci` |
| 主键 | `bigint unsigned` 自增，字段名 `id` |
| 逻辑删除 | `is_deleted tinyint(1) default 0`（MyBatis-Plus 自动过滤） |
| 时间字段 | `create_time` / `update_time`，`datetime`，由 MyBatis-Plus 自动填充 |
| 操作人字段 | `create_by` / `update_by`，存 `user_id` |
| 金额字段 | 本系统无金额，不涉及 |
| 布尔字段 | `tinyint(1)`，命名以 `is_` 开头 |
| 枚举字段 | `varchar(32)` 存编码（非数字），提升可读性与可维护性 |
| 状态字段 | `varchar(32)`，与 Java 枚举 `name()` 对应 |
| 表注释 | 所有表与关键字段必须有 `COMMENT` |

**为什么枚举存字符串而非数字**：数字枚举在排查问题时需要频繁查字典表或翻代码，"status=5" 与 "status='REPAIRED'" 的可读性差异直接影响运维效率。存储成本差异（几字节）在本系统数据规模下可忽略。

**设计说明**：

- **4 种角色共用一张表**：用户数量级在千级，角色差异通过 `role` 字段区分，学生/维修工特有字段（`college`、`work_types`）允许为空。相比分表方案（`sys_user` + `student` + `repairer`），单表在登录查询、账号管理列表页、操作日志关联上都不需要 JOIN，显著简化。代价是存在稀疏列，在本规模下可接受。
- **`uk_username` 联合 `is_deleted`**：逻辑删除后用户名应可被重新使用。若唯一索引只含 `username`，删除的用户会永久占位。
- **`password` 长度 100**：BCrypt 哈希固定 60 字符，预留余量以便未来切换算法。
- **`work_types` JSON 冗余**：维修工工种的主存储是 `repair_worker_scope` 关联表。此字段为冗余副本，用于列表页展示与快速筛选，避免 N+1 查询。**数据一致性由 Service 层保证**：维护关联表时同步更新此字段。

**关键设计说明**：

| 字段组 | 设计考虑 |
| --- | --- |
| `status` + `is_abnormal` + `is_rework` | 状态机主轴 + 两个正交标记位。异常与重修是**并行存在的属性**，一张工单可既是重修又是异常，用标记位而非状态值才能表达组合 |
| `reject_count` / `timeout_accept_count` | 分开存储，独立判定。`reject_count > 2` → 异常；`timeout_accept_count > 2` → 异常（第3次触发）。分离存储便于统计分析"哪种失败方式更常见" |
| `accept_time` | 施工超时计时器的起算点。**该字段为空即表示尚未接单**，与 `status` 有一定冗余但便于扫描 |
| `version` | 乐观锁。审核、接单等操作使用 `WHERE id=? AND version=?` 防止并发覆盖 |
| `images` / `delay_images` / `finish_images` | JSON 数组。照片数量不定，用 JSON 避免建 3 张附属表；这些字段只整体读写、不单独查询，无需建 JSON 索引 |
| `building_id` 冗余 | 来自 `room_id` 关联，用于数据权限过滤与楼栋统计，避免每次查询都 JOIN |

**索引设计依据**：

| 索引 | 服务的查询场景 |
| --- | --- |
| `idx_student_status` | 学生端"我的工单"列表，按状态筛选 |
| `idx_building_status` | 宿管端"管辖楼栋工单"，是数据权限过滤后的主查询路径 |
| `idx_worker_status` | 维修工端"我的任务池" + 自动派单的负载统计 `COUNT(*) WHERE current_worker_id IN (...) AND status IN ('ACCEPTED','DELAYED')` |
| `idx_status_priority` | 定时任务扫描 `WHERE status='PENDING_ASSIGN'` + 手动派单池按紧急度排序 |

**为什么独立建表而非在工单表加字段**：一张工单可能经历多次派单（拒单/超时回流后重新派单），每次派单的维修工、方式、时间都需独立留存，用于：① 维修工"个人全部工单记录"中的拒单/超时记录查询；② 统计"哪个维修工拒单率最高"；③ 自动派单时排除本轮已拒过的维修工。若用字段存储，多次派单历史会被覆盖。

| `repair_category` | `uk_category_name(category_name, is_deleted)` | 分类名唯一 |
| `repair_order` | `uk_order_no(order_no)` | 工单号唯一 |
| `repair_evaluation` | `uk_order(order_id)` | **一单一评** |
| `stay_application` | `uk_application_no(application_no)` | 申请单号唯一 |
| `stay_application` | `uk_batch_student(batch_id, student_id, is_deleted)` | **同批次一学生一申请** |
| `stay_batch_building` | `uk_batch_building(batch_id, building_id)` | 批次楼栋配置唯一 |
| `sys_notice_receiver` | `uk_notice_receiver(notice_id, receiver_id)` | 不重复投递 |

### 6.9.2 关键索引与对应查询场景

| 表 | 索引 | 服务的场景 |
| --- | --- | --- |
| `repair_order` | `idx_building_status` | 宿管工单列表（数据权限过滤后主路径） |
| `repair_order` | `idx_worker_status` | 维修工任务池 + 自动派单负载统计 |
| `repair_order` | `idx_status_priority` | 定时任务扫描 + 手动派单池排序 |
| `repair_dispatch` | `idx_status_dispatch_time` | 接单超时扫描任务 |
| `repair_worker_record` | `idx_worker_type` | 维修工"我的异常记录"列表 |
| `stay_application` | `idx_building_status` | 宿管留宿审核列表 |
| `sys_notice_receiver` | `idx_receiver_read` | 未读消息数角标 |

### 6.9.3 外键策略

**本设计不建立物理外键**，改由应用层保证引用完整性。

| 理由 | 说明 |
| --- | --- |
| 逻辑删除冲突 | 所有表使用逻辑删除，物理行始终存在，外键的级联/限制语义与逻辑删除不匹配 |
| 性能 | 外键检查在高频写入路径（如工单流转）上带来额外开销 |
| 分库分表预案 | 物理外键会阻碍未来的水平拆分 |
| 运维便利 | 数据修复、测试数据构造不受外键顺序约束 |

**补偿措施**：由 Service 层在删除前校验引用（如删除楼栋前校验是否存在房间），并提供定期的一致性巡检 SQL 在 CI 中作为测试用例运行。

| 项 | 值 |
| --- | --- |
| 接口 | `POST /api/v1/checkins` |
| 权限 | `ADMIN` / `DORM_MANAGER` |

**请求体：**

```json

  "bedId": 1201,
  "effectiveDate": "2026-09-01",
  "remark": "新生入学分配"
}
```

**响应：** `{"code": 0, "data": {"checkinId": 5001}}`

**错误：**

| code | 场景 |
| --- | --- |
| `40903` | 床位已被占用 |
| `40903` | 该学生已有在住床位，请先办理退宿或调宿 |
| `40902` | 床位状态已被他人变更，请刷新重试 |

**实现要点（并发安全）：**

```java
@Transactional(rollbackFor = Exception.class)
public Long assignBed(CheckinCreateDTO dto) {
    // 1. 乐观锁方式占用床位，status='EMPTY' 作为 CAS 条件
    int affected = bedMapper.occupyBed(dto.getBedId(), dto.getStudentId());
    //    UPDATE dorm_bed SET student_id=#{studentId}, status='OCCUPIED',
    //           version=version+1, checkin_time=NOW()
    //    WHERE id=#{bedId} AND status='EMPTY' AND is_deleted=0
    if (affected == 0) {
        throw new BusinessException(ResultCode.BED_OCCUPIED);
    }
    // 2. 校验学生无在住记录
    // 3. 写 dorm_checkin 记录
    // 4. 更新 dorm_room.used_count
    // 5. 推送通知给学生
}
```

**为什么用 `status='EMPTY'` 作为 CAS 条件而非仅用 `version`**：`status` 直接表达了业务不变量"床位空闲"，条件更直观且不依赖调用方先读取 version（避免读-改-写的竞态窗口）。

### 7.5.11 维修工接单

| 项 | 值 |
| --- | --- |
| 接口 | `POST /api/v1/repair/orders/{id}/accept` |
| 权限 | `REPAIRER`（被派人） |
| 前置状态 | 工单 `PENDING_ASSIGN` 且存在该维修工的 `PENDING` 派单记录 |

**响应：** `{"code": 0, "data": {"status": "ACCEPTED", "acceptTime": "2026-09-25 11:00:00"}}`

**错误：**

| code | 场景 |
| --- | --- |
| `40901` | 工单已被其他维修人员接单 |
| `40902` | 该派单记录已超时失效 |

**并发安全：**

```java
@Transactional(rollbackFor = Exception.class)
public void accept(Long orderId, Long workerId) {
    // 1. 乐观锁更新派单记录：仅当仍为 PENDING 时才可接单
    int affected = dispatchMapper.acceptDispatch(orderId, workerId);
    //    UPDATE repair_dispatch SET status='ACCEPTED', accept_time=NOW(), operate_time=NOW()
    //    WHERE order_id=? AND worker_id=? AND status='PENDING'
    if (affected == 0) {
        throw new BusinessException(ResultCode.ORDER_ALREADY_ACCEPTED);
    }
    // 2. 更新工单主表状态、accept_time、accept_type=MANUAL
    // 3. 作废该工单其他 PENDING 的派单记录（置 CANCELLED）
    // 4. 推送通知给宿管
}
```

**第一步的 CAS 是关键**：两个维修工同时点击接单，只有一个能更新成功（`status='PENDING'` 条件不满足则 affected=0），另一个收到明确提示。若不使用条件更新而先查询再更新，两者都会读到 `PENDING` 并都成功。

### 7.5.12 维修工拒单

| 项 | 值 |
| --- | --- |
| 接口 | `POST /api/v1/repair/orders/{id}/reject` |
| 权限 | `REPAIRER`（被派人） |

**请求体：** `{"rejectReason": "非本人工种范围，缺少电工证"}`

| 字段 | 必填 | 校验 |
| --- | --- | --- |
| `rejectReason` | 是 | 长度 2–500 |

**响应：**

```json
{
  "code": 0,
  "data": {
    "orderStatus": "PENDING_ASSIGN",
    "isAbnormal": false,
    "rejectCount": 1,
    "message": "已拒单，工单将重新派单"
  }
}
```

**响应（达到阈值）：**

```json
{
  "code": 0,
  "data": {
    "orderStatus": "PENDING_ASSIGN",
    "isAbnormal": true,
    "rejectCount": 2,
    "message": "已拒单，该工单累计拒单 2 次，已转入手动派单池"
  }
}
```

**服务端处理：**

1. 派单记录置 `REJECTED`，写 `reject_reason`；
2. `repair_order.reject_count++`；
3. 写 `repair_worker_record`（`record_type = REJECT`）；
4. 判定：`reject_count > 2` → `is_abnormal = 1`（拒单独立累计超过2次，即第3次触发异常）
5. 达标 → `is_abnormal = 1`，推送宿管需手动派单；未达标 → 触发自动派单重新分配（排除本轮已拒者）；
6. 工单状态**保持** `PENDING_ASSIGN`（回流不改变状态）。

> **术语说明**（根据报修业务流程.drawio）：
> - **超时未接单/超时未处理工单**：派单后超2小时未接单，与拒单**各自独立计数**
> - **超时未修好**：已接单后超时未修好，**单次即标记异常**

| 操作 | 接口 | 前置条件 |

| 项 | 值 |
| --- | --- |

### 7.6.7 宿管审核留宿申请

| 项 | 值 |
| --- | --- |
| 接口 | `POST /api/v1/stay/applications/review` |
| 权限 | `DORM_MANAGER`（所辖楼栋） |
| 说明 | **支持批量**审核 |

**请求体（批量通过）：**

```json
{
  "applicationIds": [1001, 1002, 1003],
  "approved": true
}
```

**请求体（统一驳回）：**

```json
{
  "applicationIds": [1001, 1002],
  "approved": false,
  "rejectReason": "本楼栋寒假期间封闭维修，不提供留宿"
}
```

**服务端校验（驳回时）：**

需求明确"需要等待全部留宿申请审核完毕后，统一驳回"。服务端在处理驳回请求时：

1. 统计该批次该楼栋下仍处于 `PENDING_REVIEW` 的申请数量（含本次请求之外的）；
2. 若存在**未被本次请求覆盖**的待审核申请，返回 `40903` 并提示剩余数量：

```json
{
  "code": 40903,
  "message": "尚有 12 份申请未审核，请全部审核完毕后再统一驳回",
  "data": { "pendingCount": 12 }
}
```

**设计取舍**：也可选择"允许部分驳回"。但需求原文强调"统一驳回"，且部分驳回会造成同一楼栋内学生收到不一致的处理结果，与"统一"的管理意图不符。本设计遵循需求原文，同时通过明确的错误提示引导宿管完成审核。

## 7.8 统计报表模块

> 以下接口均为 **V2** 功能。V1 仅实现基础计数（如楼栋入住率），接口形态保持一致以便平滑扩展。

### 7.8.1 入住统计

| 项 | 值 |
| --- | --- |
| 接口 | `GET /api/v1/stats/occupancy` |
| 权限 | 宿管（所辖）/ `ADMIN` |

**参数：** `buildingId`（可选）

**响应：**

```json
{
  "code": 0,
  "data": {
    "totalBedCount": 480,
    "usedBedCount": 456,
    "emptyBedCount": 24,
    "occupancyRate": 95.0,
    "buildings": [
      {
        "buildingId": 1,
        "buildingName": "紫荆苑1号楼",
```

**统计口径说明（必须统一）：**

| 指标 | 定义 |
| --- | --- |

| `occupancyRate` | `usedCount / bedCount * 100`，保留 1 位小数，`bedCount = 0` 时返回 `0.0` |

**口径统一是本设计的显式约束**：拟题报告将"批量操作与统计口径的一致性"列为难点。做法是将统计口径固化为 SQL 视图或 Mapper 中的常量，所有报表复用，避免各页面各自实现导致数字对不上。

| --- | --- |

**安全实现要点（重要）：**

| 风险 | 防护措施 |
| --- | --- |
| 路径穿越 | 文件名**不使用用户提供的名称**，服务端生成 UUID + 原扩展名 |

| 磁盘占满 | 定时任务清理未被业务引用的孤儿文件 |

**存储路径规则：** `/upload/{yyyy}/{MM}/{dd}/{uuid}.{ext}`，按日期分目录避免单目录文件数过多。

## 8.2 状态与并发约束

### 8.2.1 状态机约束

| # | 约束 |
| --- | --- |
| ST1 | 所有状态变更**必须**通过状态机类执行，禁止在 Service 中直接 `setStatus()` |
| ST2 | 非法流转抛出 `StateConflictException`，返回 `40901` |
| ST3 | 状态变更与业务副作用（写日志、发通知）必须在**同一事务**内 |
| ST4 | 状态机定义集中在一处（`statemachine/` 包），便于对照需求评审 |

**为什么强制走状态机**：若允许任意位置 `setStatus()`，则状态变更逻辑会分散到数十个方法中，无法回答"什么情况下工单会变成已维修"这类问题。集中定义后，状态机类即是**可执行的需求文档**，且便于编写覆盖全部流转路径的单元测试。

**状态机实现方式：**

```java
public enum RepairOrderStatusEnum {
    DRAFT, PENDING_REVIEW, REJECTED, PENDING_ASSIGN,
    ACCEPTED, DELAYED, REPAIRED, CONFIRMED, ARCHIVED;

    /** 合法流转表 */
    private static final Map<RepairOrderStatusEnum, Set<RepairOrderStatusEnum>> TRANSITIONS = Map.of(
        DRAFT,          Set.of(PENDING_REVIEW),
        PENDING_REVIEW, Set.of(REJECTED, PENDING_ASSIGN, DRAFT),
        REJECTED,       Set.of(PENDING_REVIEW, DRAFT),
        PENDING_ASSIGN, Set.of(ACCEPTED),          // 回流到自身也需显式允许
        ACCEPTED,       Set.of(DELAYED, REPAIRED, PENDING_ASSIGN),
        DELAYED,        Set.of(DELAYED, REPAIRED, PENDING_ASSIGN),
        REPAIRED,       Set.of(CONFIRMED, PENDING_ASSIGN),
        CONFIRMED,      Set.of(ARCHIVED),
        ARCHIVED,       Set.of()
    );

    public boolean canTransitionTo(RepairOrderStatusEnum target) {
        return TRANSITIONS.getOrDefault(this, Set.of()).contains(target);
    }
}
```

### 8.2.2 并发控制约束

| # | 场景 | 控制手段 |
| --- | --- | --- |
| CC1 | 两名维修工同时接单 | `UPDATE ... WHERE status='PENDING'` 条件更新（CAS） |
| CC2 | 两名宿管同时审核同一工单 | 工单 `version` 乐观锁 |
| CC3 | 管理员同时分配同一床位 | `UPDATE ... WHERE status='EMPTY'` 条件更新 |
| CC4 | 学生重复点击提交 | 前端禁用按钮 + 后端幂等（`@Idempotent` 注解 + Redis/本地缓存 token） |
| CC5 | 定时任务与人工操作竞争 | 定时任务处理前重新校验状态，状态已变则跳过 |
| CC6 | 定时任务重复执行 | V1 单实例部署（见 8.6）；V2 多实例时引入分布式锁 |

**原则：所有并发控制依赖数据库的条件更新或版本号，不依赖应用层锁。** 应用层锁（`synchronized`）在多实例部署下失效，且容易因异常未释放而死锁。

### 8.3.4 CORS 配置约束

```java
// 仅允许开发环境的前端源；生产环境由 Nginx 同源代理，无需跨域
registry.addMapping("/api/**")
        .allowedOriginPatterns("http://localhost:[*]", "http://127.0.0.1:[*]")
        .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
        .allowedHeaders("*")
        .allowCredentials(true)
        .maxAge(3600);
```

**生产环境禁止使用 `allowedOrigins("*")`** —— 与 `allowCredentials(true)` 组合会导致浏览器拒绝，而若为使其生效关闭凭据则引入 CSRF 风险。生产环境应通过 Nginx 反向代理做到同源，从根本上消除 CORS 需求。

## 8.5 性能约束

拟题报告明确："系统在模拟数据规模（**千级学生、百级宿舍**）下运行稳定，常规页面操作**响应时间不超过 2 秒**。"

### 8.5.1 数据规模假设

| 对象 | 预估规模 |
| --- | --- |
| 用户 | 1,000 – 5,000 |
| 楼栋 | 10 – 30 |
| 房间 | 500 – 1,000 |
| 床位 | 2,000 – 6,000 |
| 报修工单（年） | 3,000 – 10,000 |
| 留宿申请（学期） | 500 – 2,000 |
| 站内消息（年） | 50,000 – 200,000 |

在此规模下，**单表数据量不会成为瓶颈**，无需分库分表。设计重点是索引正确性与避免 N+1 查询。

### 8.5.2 性能指标

| 指标 | 目标值 |
| --- | --- |
| 常规页面操作响应时间 | ≤ 2 s（P95） |
| 列表查询响应时间 | ≤ 1 s（分页 ≤ 20 条） |
| 统计报表响应时间 | ≤ 3 s |
| 登录响应时间 | ≤ 1 s |
| 文件上传（10 MB） | ≤ 5 s |
| 并发用户数 | ≥ 50 |
| 系统可用性（课程演示期） | ≥ 99% |

### 8.5.3 性能保障措施

| 措施 | 说明 |
| --- | --- |
| **分页强制** | 所有列表接口必须分页，`size` 上限 100，杜绝全表返回 |
| **索引覆盖** | 见 6.9.2，核心查询均有索引支撑 |
| **避免 N+1** | 列表页关联数据（如维修工姓名）用 JOIN 或批量查询后在内存组装，禁止循环内查询 |
| **大字段延迟加载** | 列表接口不返回 `description` / `images` 等大字段，仅在详情接口返回 |
| **统计结果缓存** | 统计接口结果缓存 5 分钟（Caffeine），避免频繁全表聚合 |
| **导出异步化** | 大数据量导出（> 10,000 行）改为异步任务 + 文件下载 |
| **连接池配置** | HikariCP `maximum-pool-size` 20，`connection-timeout` 30s |

**关于"2 秒"的可行性判断**：在本数据规模下，只要索引正确、无 N+1，绝大多数查询在 50ms 内完成。**2 秒的挑战不在数据库，而在典型错误**——全表返回、循环查询、缺少索引。因此性能约束的落地方式是**代码评审检查项 + 慢 SQL 日志监控**，而非引入缓存层或读写分离等重架构。

## 8.7 需求基线冲突与裁决建议

在编制本文档过程中，发现需求文档之间存在 **5 处不一致**。这些冲突若不裁决，将导致开发与验收标准分歧。以下逐项列出并给出裁决建议，**需经团队与指导教师确认后固化**。

### 冲突 1：角色数量（3 个 vs 4 个）

| 来源 | 表述 |
| --- | --- |
| 拟题报告 | "按'**管理员—宿管员—学生**'三类角色划分功能与数据权限" |
| 路演 PPT | "3 个角色：学生 · 宿管 · 系统管理员" |
| **《用户故事地图》** | **独立列出"1.3 维修工角色"完整功能表**（11 条功能） |
| 报修流程 | 维修工是接单、拒单、延期、完工的操作主体 |
| 留宿流程 | 参与角色仅"学生、宿管、系统管理员" |

**裁决建议：采用 4 角色模型（含维修工）。**

**理由：**
1. 报修流程中维修工承担了 4 个关键决策点（接单/拒单/延期/完工），若将其归入其他角色，权限将无法正确划分——例如"维修工只能看自己被派的工单"与"宿管能看全楼栋工单"是两个不同的数据范围，必须用不同角色区分；
2. 用户故事地图是**粒度最细、最新**的需求基线，已为维修工列出完整功能表，说明团队在细化需求时已识别该角色的独立性；
3. 拟题报告写作时可能将维修工笼统归入"宿管员"职责（宿管负责联系维修人员），但流程细化后该简化不再成立。

**需同步修订**：拟题报告的"三类角色"表述、PPT 的"3 个角色"页面，应更新为四类角色。

### 冲突 2：留宿模块的版本归属（V1 vs V2）

| 来源 | 表述 |
| --- | --- |
| **《用户故事地图》** | **学生全部留宿功能标 V2**；宿管全部留宿功能标 V2；管理员留宿功能标 V2 |
| 路演 PPT — V1 页 | 学生："**提交假期留宿申请**"；宿管："**审核学生假期留宿申请**" |
| 路演 PPT — V2 页 | 宿管："留宿名单查看与人数统计"；管理员："留宿时段导入 · 名单导出统计" |

**裁决建议：留宿模块整体归 V2，V1 仅交付申请的提交与审核最小闭环（可选）。**

**理由：**
1. 用户故事地图标 V2 是**逐条标注**的结果，粒度远细于 PPT 的页面级归纳，可信度更高；
2. PPT 的 V1 页强调的是"跑通核心业务闭环"，而 V1 的核心闭环是**报修**（PPT 首页副标题即为"优化报修流程"）；
3. 从工作量看，留宿模块包含批次配置、楼栋级截止时间、锁定机制、统一驳回等复杂规则，与报修的工程量相当，两者同时放入 V1 会显著挤压迭代周期；
4. 留宿是**周期性低频业务**（寒暑假各一次），而报修是**高频日常业务**，优先级上应让位于报修。

**若课程进度允许**，可将"提交申请 + 审核"提前至 V1（如 PPT 所述），锁定、统一驳回、统计导出留在 V2。**建议由指导教师根据 16 周节奏确认。**

### 冲突 3：接单超时阈值未在前置约束中定义

| 来源 | 表述 |
| --- | --- |
| 报修流程 - 前置约束 #4 | 只定义了**施工超时**：常规 24h、紧急 6h（"接单后…未修好"） |
| 报修流程 - 步骤 5 分支① | "**超过时限**没有接单，计入超时未处理工单记录"——**未给出具体时限**，仅称"时限" |
| 《用户故事地图》 | 2.3 步骤 4 分支 A："**2 小时内无接单** → 计入超时未接单记录" |
| 拟题报告 / 路演 PPT | 均未提及接单时限 |

**裁决建议：接单超时阈值 = 2 小时，与施工超时（24h/6h）为两个独立计时器。**

**理由：** 前置约束 #4 描述的是"接单**后**"的施工超时，与"未接单"的接单超时是两个不同阶段，二者并不矛盾——前置约束只是未覆盖接单超时这一阶段。用户故事地图作为粒度最细的需求基线，明确给出了 2 小时这一数值，据此填入。

**注意**：2 小时为本设计**拟定的默认值**（与施工超时的 24h/6h 同属可配置项，见 [5.4.1](#541-阈值配置化)）。正式需求文档的前置约束中应补充该阈值，并由指导教师确认。

**同时建议**：在正式需求文档的前置约束中补充第 5 条，明确接单超时阈值，避免后续歧义。

### 冲突 4：异常工单的计数口径

| 来源 | 表述 |
| --- | --- |
| 报修流程 步骤 5 分支①② | "工单**超时/被拒**达到两次，工单记为异常工单" |
| 报修流程 步骤 6 情况三 | "超时未修工单，计入超时工单记录，工单记为异常工单"（**无次数门槛**） |

**歧义点**："超时/被拒达到两次"是指：

| 方案 | 含义 |
| --- | --- |
| ~~A（已废弃）~~ | ~~超时未接次数 + 拒单次数 **之和** ≥ 2~~ |
| **B（本设计采用）** | 超时未处理工单超过2次（第3次触发）**或** 拒单超过2次（第3次触发）（各自独立判定） |

**裁决建议：采用方案 B（独立计数）。**

**理由：** 根据 `报修业务流程.drawio` 中的流程图，超时未处理工单（超时未接单）与拒单是**两个独立的分支**，分别计数：
- 超时未处理工单（超时未接单）分支：超2小时未接单 → 计入超时未处理工单记录 → 超过2次（第3次） → 异常工单
- 拒单分支：维修人员拒绝接单 → 计入拒单记录 → 超过2次（第3次） → 异常工单

两个分支各自独立计数，互不影响。drawio 约束中明确"总维修人员数量超过 2"，意味着可能存在某个工种只有一人维修工的情况，此时拒单和超时是独立事件。

**同时明确**："超时未修好"（已接单后超时）**无次数门槛**，单次即标记异常——因为已接单意味着维修工承诺了责任，超时的严重性高于未接单。

**实现方式**：数据库保留 `reject_count` 与 `timeout_accept_count` 两个独立字段，分别统计拒单次数与超时未接次数。

### 冲突 5："撤销申请"在报修流程中的可用范围

| 来源 | 表述 |
| --- | --- |
| 报修流程 步骤 2 | "学生填写报修工单，**填写阶段**可保存修改、提交、**撤销**申请；**派单后不可撤销**" |
| 报修流程 步骤 3 | 审核不通过 → 工单退回学生 → "学生可**重新填写**报修工单" |

**已确认**：
- `DRAFT` 状态：允许撤销（回到草稿，可继续编辑）
- `PENDING_REVIEW` 状态：允许撤销（回到 `DRAFT`，派单前可撤销）
- `PENDING_ASSIGN` 状态（已派单）：**不可撤销**——此时工单已派给维修人员，单方面撤销会打乱派单安排。若学生确需取消，应走线下沟通由宿管处理。

### 9.2.1 Nginx 路由规则

| 路径 | 目标 | 说明 |
| --- | --- | --- |
| `/` | 前端静态文件 | SPA，需 `try_files` 回退到 `index.html` |
| `/api/**` | `http://backend:8080` | 反向代理，去除 CORS 需求 |
| `/upload/**` | 上传目录 | 静态文件直接由 Nginx 返回，不经过后端 |
| `/swagger-ui/**` | `http://backend:8080` | 仅 dev/test 环境开放 |

**SPA 回退配置（易错点）：**

```nginx
location / {
    root /usr/share/nginx/html;
    index index.html;
    try_files $uri $uri/ /index.html;   # 关键：未匹配到文件时回退到 index.html
}
```

**缺少 `try_files` 会导致刷新页面 404**：Vue Router 使用 history 模式时，`/repair/orders/8001` 这类路径在服务器上不存在对应文件。若不回退到 `index.html`，用户刷新详情页会看到 Nginx 404，而非前端路由正常渲染。

## 9.3 容器化配置

### 9.3.1 后端 Dockerfile

```dockerfile
# ---------- 构建阶段 ----------
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build
# 先复制 pom 单独下载依赖，利用 Docker 层缓存
COPY pom.xml .
RUN mvn dependency:go-offline -B
COPY src ./src
RUN mvn clean package -DskipTests -B

# ---------- 运行阶段 ----------
FROM eclipse-temurin:17-jre-jammy
WORKDIR /app

# 时区设置（关键：避免日志与数据库时间相差 8 小时）
ENV TZ=Asia/Shanghai
RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone

# 非 root 用户运行（安全要求）
RUN groupadd -r appuser && useradd -r -g appuser appuser

COPY --from=builder /build/target/*.jar app.jar
RUN mkdir -p /app/logs /app/upload && chown -R appuser:appuser /app
USER appuser

EXPOSE 8080

# 使用 exec 形式，确保 JVM 接收 SIGTERM 实现优雅停机
ENTRYPOINT ["java", \
  "-XX:+UseContainerSupport", \
  "-XX:MaxRAMPercentage=70", \
  "-Djava.security.egd=file:/dev/./urandom", \
  "-jar", "app.jar"]
```

**关键设计说明：**

| 项 | 理由 |
| --- | --- |
| 多阶段构建 | 构建镜像（含 Maven ~500MB）与运行镜像分离，最终镜像仅 ~250MB |
| 先 COPY pom 再 COPY src | 源码变更时不重新下载依赖，CI 构建时间从 ~3min 降至 ~40s |
| `TZ=Asia/Shanghai` | **不设置会导致 JVM 默认 UTC**，业务时间与开发预期差 8 小时，是极高频的踩坑点 |
| 非 root 用户 | 容器逃逸后攻击者获得的是普通用户权限 |
| `exec` 形式 ENTRYPOINT | shell 形式（`ENTRYPOINT java -jar ...`）下 JVM 是 shell 的子进程，收不到 `SIGTERM`，导致停机时等待超时被 `SIGKILL`，事务中断 |
| `MaxRAMPercentage=70` | 让 JVM 感知容器内存限制并按比例设置堆，避免堆超限被 OOM Killer 杀死 |

### 9.3.3 docker-compose.yml

```yaml
version: '3.8'

services:
  mysql:
    image: mysql:8.0
    container_name: dorm-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: dormitory_mis
      MYSQL_USER: ${MYSQL_USER}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD}
      TZ: Asia/Shanghai
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
      - --default-time-zone=+08:00
      - --max_connections=200
      - --innodb_buffer_pool_size=512M
    volumes:
      - mysqldata:/var/lib/mysql
      - ./sql/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    networks:
      - dorm-net
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-p${MYSQL_ROOT_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 10

  backend:
    image: ${REGISTRY}/dorm-backend:${TAG}
    container_name: dorm-backend
    restart: unless-stopped
    depends_on:
      mysql:
        condition: service_healthy
    environment:
      SPRING_PROFILES_ACTIVE: prod
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/dormitory_mis?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useSSL=false
      SPRING_DATASOURCE_USERNAME: ${MYSQL_USER}
      SPRING_DATASOURCE_PASSWORD: ${MYSQL_PASSWORD}
      JWT_SECRET: ${JWT_SECRET}
      TZ: Asia/Shanghai
    volumes:
      - uploads:/app/upload
      - ./logs/backend:/app/logs
    networks:
      - dorm-net
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/actuator/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 60s

  frontend:
    image: ${REGISTRY}/dorm-frontend:${TAG}
    container_name: dorm-frontend
    restart: unless-stopped
    depends_on:
      - backend
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - uploads:/usr/share/nginx/upload:ro
      - ./nginx/certs:/etc/nginx/certs:ro
    networks:
      - dorm-net

volumes:
  mysqldata:
  uploads:

networks:
  dorm-net:
    driver: bridge
```

**关键设计说明：**

| 项 | 理由 |
| --- | --- |
| `depends_on` + `condition: service_healthy` | 简单的 `depends_on` 只保证容器**启动顺序**，不保证 MySQL **就绪**。后端可能在 MySQL 初始化完成前启动导致连接失败。健康检查解决此问题 |
| `uploads` 命名卷共享 | 后端写入上传文件，Nginx 需要读取以提供静态访问。共享卷是两者交换文件的通道 |
| `restart: unless-stopped` | 服务器重启或容器崩溃后自动恢复；手动停止的容器不会被自动拉起 |
| 密码走环境变量 | 禁止在 compose 文件硬编码密码——该文件会提交到 Git |
| `default-time-zone=+08:00` | 数据库时区，与 JVM 时区保持一致，避免时间字段读写偏移 |

## 9.4 CodeArts 流水线

拟题报告的过程目标要求："使用 Git 在 CodeArts 代码托管中协作开发，通过编码规范性检查，基于 Maven 实现自动构建与持续集成"、"完成应用的 Docker 镜像打包与推送，并在 CodeArts 上完成部署与发布"。

### 9.4.1 流水线阶段划分

```
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│  代码    │→│  构建    │→│  测试    │→│  镜像    │→│  部署    │
│  检查    │  │         │  │         │  │  推送    │  │         │
└─────────┘  └─────────┘  └─────────┘  └─────────┘  └─────────┘
    │            │            │            │            │
 Checkstyle   mvn package   mvn test    docker      docker
  ESLint      -DskipTests   JUnit       build&push  compose up
                                                  health check
```

### 9.4.2 触发策略

| 事件 | 执行阶段 |
| --- | --- |
| Push 到 `feature/*` | 代码检查 → 构建 → 测试 |
| Push 到 `develop` | 全部阶段，部署到 **test** 环境 |
| Push 到 `main` / Tag `v*` | 全部阶段，部署到 **prod** 环境（需人工审批） |
| Merge Request | 代码检查 → 构建 → 测试 |

**生产部署必须有人工审批卡点**：自动化部署到生产环境的流水线若无审批环节，一次误提交即可导致线上故障。

### 9.4.3 流水线任务配置要点

**代码检查阶段：**

| 检查项 | 工具 | 失败处理 |
| --- | --- | --- |
| Java 代码规范 | Checkstyle（Maven 插件） | 阻断 |
| 前端代码规范 | ESLint | 阻断 |
| 依赖漏洞扫描 | CodeArts 内置 | 仅告警 |
| 单元测试覆盖率 | JaCoCo | 低于 60% 告警 |

**构建阶段：**

```bash

```

**测试阶段：**

```bash
mvn test -B
# 生成 JaCoCo 报告并归档
```

**镜像推送阶段：**

```bash
docker build -t ${REGISTRY}/dorm-backend:${TAG} ./backend
```

**部署阶段：**

## 9.5 配置管理

### 9.5.1 配置分层

| 层级 | 载体 | 内容 |
| --- | --- | --- |
| 默认配置 | `application.yml` | 与环境的无关配置 |
| 环境配置 | `application-{profile}.yml` | 数据源、日志级别、外部服务地址 |
| 环境变量 | Docker Compose `environment` / `.env` | **密码、密钥等敏感信息** |
| 数据库配置 | `sys_config` 表 | 业务规则阈值（超时时间等） |

**敏感信息禁止入库的三个理由**：

1. 配置文件提交到 Git 后，密码永久留存于历史记录，即使后续删除也能从历史检出；
2. CodeArts 流水线的日志可能回显配置文件内容；
3. 密钥轮换需修改代码并重新提交，而非仅更新环境变量。

### 9.5.2 关键配置项

```yaml
# application-prod.yml
server:
  port: 8080
  shutdown: graceful            # 优雅停机，等待在途请求完成

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000
      max-lifetime: 1800000     # 小于 MySQL wait_timeout，避免使用已断开的连接
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 50MB
  jackson:
    date-format: yyyy-MM-dd HH:mm:ss
    time-zone: Asia/Shanghai
    default-property-inclusion: non_null

mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true
  global-config:
    db-config:
      logic-delete-field: isDeleted
      logic-delete-value: 1
      logic-not-delete-value: 0

jwt:
  secret: ${JWT_SECRET}         # 从环境变量注入
  expire-hours: 24
  header: Authorization
  prefix: "Bearer "

logging:
  level:
    root: INFO
    com.dorm.mis: INFO
    com.dorm.mis.mapper: DEBUG  # 打印 SQL，便于排查性能问题
  file:
    name: /app/logs/dormitory-mis.log
  logback:
    rollingpolicy:
      max-file-size: 100MB
      max-history: 30
```

**`max-lifetime: 1800000` 的必要性**：MySQL 默认 `wait_timeout` 为 8 小时。若连接池中的空闲连接被 MySQL 服务端关闭而池中未感知，应用取到该连接会抛 `Communications link failure`。将 `max-lifetime`（30 分钟）设为小于服务端超时，保证连接在使用前已被回收重建。

## 9.6 发布与回滚

### 9.6.1 发布流程

| 步骤 | 操作 | 验证 |
| --- | --- | --- |
| 1 | 合并 MR 到 `main`，打 Tag | Tag 符合 `v{semver}` |
| 2 | 流水线构建镜像并推送 | 镜像 Tag 可查 |
| 3 | **数据库迁移预检** | 检查 Flyway 脚本是否含破坏性变更 |
| 4 | 人工审批 | 确认变更内容与影响范围 |
| 5 | 部署到生产 | `docker compose up -d` |
| 6 | 健康检查 | `/actuator/health` 返回 `UP` |
| 7 | 冒烟测试 | 登录、报修提交、工单查询 |
| 8 | 观察日志 15 分钟 | 无异常堆栈、无 5xx 激增 |

### 9.6.2 数据库变更的安全要求

**破坏性变更必须分两次发布**（扩展-收缩模式）：

| 变更类型 | 危险做法 | 安全做法 |
| --- | --- | --- |
| 删除字段 | 发布时直接 `DROP COLUMN` | ① 本次发布停止代码写入该字段；② 观察一个版本；③ 下次发布再 `DROP` |
| 重命名字段 | 发布时 `RENAME COLUMN` | ① 新增新字段；② 双写；③ 迁移数据；④ 切换读；⑤ 下次发布删除旧字段 |
| 修改字段类型 | `ALTER TABLE MODIFY` | 新增字段 + 迁移数据 + 切换，避免锁表 |
| 添加非空字段 | 直接 `ADD COLUMN NOT NULL` | 先加可空字段 → 回填数据 → 再改为非空 |

**理由**：应用与数据库的发布不是原子的。发布过程中新旧代码并存，若数据库结构变更与代码不兼容，会在发布窗口内产生故障。

### 9.6.3 回滚方案

| 场景 | 回滚方式 | 耗时 |
| --- | --- | --- |
| 应用问题（代码 bug） | 切换到上一个镜像 Tag 重启 | ~1 min |
| 配置问题 | 恢复上一个 `.env` / 环境变量重启 | ~1 min |
| 数据库结构问题 | 执行对应 `U{n}__rollback_*.sql` | ~5 min |
| 数据损坏 | 从备份恢复 | ~30 min |
| 前端问题 | 切换前端镜像 Tag | ~30 s |

**回滚命令：**

```bash
# 回滚到指定版本
export TAG=v1.0.0
docker compose pull backend frontend
docker compose up -d --no-deps backend frontend
curl -f http://localhost:8080/actuator/health
```

**回滚预案要求**：每个涉及数据库变更的发布，必须同时准备 `U{n}__rollback_*.sql` 并**在测试环境验证过回滚脚本可执行**。未经测试的回滚脚本在故障时不可依赖。

### 9.7.3 日志规范

| 级别 | 使用场景 | 示例 |
| --- | --- | --- |
| `ERROR` | 系统异常、业务失败需人工介入 | 数据库连接失败、定时任务异常 |
| `WARN` | 可恢复的异常、潜在问题 | 乐观锁冲突重试、文件清理失败 |
| `INFO` | 关键业务节点 | 工单状态流转、用户登录、配置变更 |
| `DEBUG` | 调试信息（仅 dev） | SQL 参数、方法入参 |

**日志中禁止输出**：密码、完整身份证号、完整手机号（需掩码）、JWT Token、文件内容。

**关键业务操作必须记录 INFO 日志**：

```java
log.info("工单状态流转: orderNo={}, {} -> {}, operator={}, reason={}",
         order.getOrderNo(), fromStatus, toStatus, operatorId, reason);
```

**为什么状态流转必须打日志**：状态机是本系统的核心，出现争议时（如学生投诉工单被误驳回），日志是唯一的追溯依据。日志需包含**状态前后值、操作人、原因**三个要素。

### 9.7.4 日志文件管理

```xml
<!-- logback-spring.xml 关键配置 -->
<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>/app/logs/dormitory-mis.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
        <fileNamePattern>/app/logs/dormitory-mis.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
        <maxFileSize>100MB</maxFileSize>
        <maxHistory>30</maxHistory>
        <totalSizeCap>5GB</totalSizeCap>
    </rollingPolicy>
    <encoder>
        <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId}] - %msg%n</pattern>
        <charset>UTF-8</charset>
    </encoder>
</appender>
```

**`totalSizeCap` 必须设置**：仅设 `maxHistory` 不设 `totalSizeCap` 时，若单日日志量异常增大，30 天的日志可能占满磁盘。`totalSizeCap` 提供绝对上限。

**`traceId` 用于链路追踪**：在 `JwtAuthenticationFilter` 或专门的 Filter 中生成 `traceId` 放入 MDC，使同一请求的所有日志可通过 `traceId` 串联，便于排查跨层问题。

## 9.8 备份与恢复

### 9.8.1 备份策略

| 类型 | 频率 | 保留 | 内容 |
| --- | --- | --- | --- |
| 全量备份 | 每日 02:00 | 7 天 | 完整数据库 |
| 增量备份 | 每 6 小时 | 3 天 | binlog |
| 上传文件备份 | 每日 02:30 | 7 天 | `/app/upload` 目录 |
| 发布前备份 | 每次生产发布前 | 30 天 | 完整数据库 |

**发布前备份是硬性要求**：数据库变更失败时，从备份恢复是最后手段。若无发布前备份，破坏性变更将造成不可逆的数据损失。

### 9.8.2 备份脚本

```bash
#!/bin/bash
# deploy/scripts/backup.sh
set -euo pipefail

BACKUP_DIR=/data/backup
DATE=$(date +%Y%m%d_%H%M%S)
KEEP_DAYS=7

mkdir -p "${BACKUP_DIR}"

# 1. 数据库备份（含存储过程、触发器、事件）
docker exec dorm-mysql mysqldump \
    -uroot -p"${MYSQL_ROOT_PASSWORD}" \
    --single-transaction \
    --routines \
    --triggers \
    --events \
    --set-gtid-purged=OFF \
    dormitory_mis | gzip > "${BACKUP_DIR}/db_${DATE}.sql.gz"

# 2. 校验备份文件非空（关键：空文件意味着备份失败但脚本继续了）
if [ ! -s "${BACKUP_DIR}/db_${DATE}.sql.gz" ]; then
    echo "ERROR: 备份文件为空，备份失败" >&2
    exit 1
fi

# 3. 上传文件备份
tar -czf "${BACKUP_DIR}/upload_${DATE}.tar.gz" -C /var/lib/docker/volumes uploads 2>/dev/null || true

# 4. 清理过期备份
find "${BACKUP_DIR}" -name "db_*.sql.gz" -mtime +${KEEP_DAYS} -delete
find "${BACKUP_DIR}" -name "upload_*.tar.gz" -mtime +${KEEP_DAYS} -delete

echo "备份完成: db_${DATE}.sql.gz ($(du -h "${BACKUP_DIR}/db_${DATE}.sql.gz" | cut -f1))"
```

**`--single-transaction` 的必要性**：InnoDB 下该参数使备份在一致性快照中执行，不阻塞业务写入。不加此参数会在备份期间锁表，导致业务不可用。

**备份文件非空校验**：`mysqldump` 失败时（如密码错误）可能产生 0 字节文件，若不加校验，脚本会正常退出且清理任务会保留这个无效备份，等到真正需要恢复时才发现备份不可用。

### 9.8.3 定时任务配置

```bash
# crontab -e
0 2 * * *   /opt/dormitory/deploy/scripts/backup.sh >> /var/log/dorm-backup.log 2>&1
30 2 * * *  /opt/dormitory/deploy/scripts/cleanup-orphan-files.sh >> /var/log/dorm-cleanup.log 2>&1
0 3 * * 0   /opt/dormitory/deploy/scripts/verify-backup.sh >> /var/log/dorm-verify.log 2>&1
```

**每周的备份验证任务必不可少**：备份存在不等于备份可用。`verify-backup.sh` 在临时数据库中恢复最近的备份并执行一致性检查（表数量、关键表行数），确保恢复流程确实可行。

### 9.8.4 恢复流程

```bash
# 1. 停止应用（防止恢复期间写入）
docker compose stop backend

# 2. 解压备份
gunzip -c /data/backup/db_20260925_020000.sql.gz > /tmp/restore.sql

# 3. 恢复（先删后建，确保干净）
docker exec -i dorm-mysql mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" \
    -e "DROP DATABASE IF EXISTS dormitory_mis; CREATE DATABASE dormitory_mis CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
docker exec -i dorm-mysql mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" dormitory_mis < /tmp/restore.sql

# 4. 恢复上传文件
tar -xzf /data/backup/upload_20260925_020000.tar.gz -C /var/lib/docker/volumes/

# 5. 启动应用
docker compose start backend

# 6. 验证
curl -f http://localhost:8080/actuator/health
```

**恢复演练要求**：每学期至少执行一次完整的恢复演练，验证 RTO（恢复时间目标）。

| 指标 | 目标 |
| --- | --- |
| RPO（恢复点目标，可容忍的数据丢失） | ≤ 6 小时（binlog 增量） |
| RTO（恢复时间目标） | ≤ 30 分钟 |

## 9.9 常见故障处置

### 9.9.1 故障速查表

| 现象 | 可能原因 | 排查步骤 | 处置 |
| --- | --- | --- | --- |
| 前端白屏 | 静态资源 404 / JS 报错 | 浏览器控制台看报错；`docker logs dorm-frontend` | 检查镜像是否正确构建；确认 Nginx root 路径 |
| 刷新页面 404 | Nginx 缺 `try_files` | 检查 `nginx.conf` | 补 `try_files $uri $uri/ /index.html` |
| 接口 401 | Token 过期 / 未携带 | 看请求头是否有 `Authorization` | 重新登录；检查前端拦截器 |
| 接口 403 | 权限不足 / 数据越权 | 确认用户角色与数据归属 | 检查 `@DataScope` 配置 |
| 后端启动失败 | 数据库连不上 | `docker logs dorm-backend` 看堆栈 | 确认 MySQL 健康；检查连接串 |
| 连接池耗尽 | 慢查询 / 连接泄漏 | `SHOW PROCESSLIST` | 定位慢 SQL；检查 `max-lifetime` |
| 时间相差 8 小时 | 时区配置缺失 | `docker exec dorm-backend date` | 补 `TZ=Asia/Shanghai`；JDBC 串加 `serverTimezone` |
| 上传文件 404 | Nginx 读不到卷 | `docker exec dorm-frontend ls /usr/share/nginx/upload` | 检查卷共享配置 |
| 定时任务重复执行 | 多实例部署 | `docker ps` 看 backend 实例数 | 约束为单实例，或引入分布式锁 |
| 磁盘占满 | 日志/备份/上传文件堆积 | `df -h`；`du -sh /app/logs /data/backup` | 清理过期文件；调整保留策略 |
| 中文乱码 | 字符集不一致 | 检查库/表/连接三级字符集 | 统一 `utf8mb4` |

### 9.9.2 紧急联系与升级

| 级别 | 场景 | 响应 |
| --- | --- | --- |
| P0 | 系统完全不可用 | 立即回滚至上一版本 |
| P1 | 核心功能不可用（报修提交失败） | 30 分钟内定位，1 小时内修复或回滚 |
| P2 | 非核心功能异常（统计报表错误） | 当日修复 |
| P3 | 体验问题（样式错位） | 下一迭代修复 |

## 10.2 术语表

| 术语 | 英文/编码 | 说明 |
| --- | --- | --- |
| 工单 | Repair Order | 学生提交的报修申请单，本系统核心业务对象 |
| 派单 | Dispatch | 将工单分配给维修工的动作，分自动与手动两种 |
| 强制派单 | Force Dispatch | 宿管指定维修工的派单方式，系统自动接单 |
| 接单 | Accept | 维修工确认承接工单 |
| 拒单 | Reject | 维修工拒绝承接工单，需填写原因 |
| 接单超时 | Accept Timeout | 派单后超过阈值（默认 2 小时）未接单，计入**超时未处理工单记录** |
| 施工超时 | Arrive Timeout | 接单后超过阈值（常规 24h / 紧急 6h）未修好的判定 |
| 超时未修好 | Handle Timeout | 因施工超时而生成的异常记录类型（TIMEOUT_HANDLE），单次即标记异常；区别于"超时未处理工单"（派单后超时未接单） |
| 超时未处理工单 | Timeout Accept Record | 派单后超过2小时未接单（既没接单也没拒单）生成的记录；与"超时未修好工单"是两个独立概念 |
| 延期工单记录 | Delay Record | 维修工申请延期时写入的记录（DELAY），用于统计延期次数 |
| 异常工单 | Abnormal Order | 满足以下任一条件的工单：①超时未处理工单超过2次（第3次触发）；②拒单超过2次（第3次触发）；③超时未修好1次。进入**手动派单池**，不再参与自动派单 |
| 重修工单 | Rework Order | 学生确认未修好后申请复修的工单 |
| 回流 | Reflow | 工单被拒/超时后重新进入派单池 |
| 维修延期 | Delay | 维修工因故无法一次完成，申请延长工期（写入延期工单记录） |
| 留宿批次 | Stay Batch | 一次留宿申请的完整周期（如"2026年寒假留宿"） |
| 锁定 | Lock | 宿管冻结留宿申请编辑的操作，不改变申请状态 |
| 数据范围 | Data Scope | 角色可访问的数据行集合 |
| 站内消息 | In-site Notice | 系统内部消息，区别于短信/邮件等外部渠道 |
| 扇出 | Fan-out | 一条群发通知展开为多条接收明细的过程 |
| 逻辑删除 | Logical Delete | 通过标记位而非物理删除，保留数据可追溯性 |
| 状态机 | State Machine | 定义状态集合与合法流转路径的模型 |
| 乐观锁 | Optimistic Lock | 通过版本号或条件更新实现无锁并发控制 |
| 数据权限 | Data Permission | 控制可访问数据行范围的权限层次 |
| 功能权限 | Function Permission | 控制接口/按钮可访问性的权限层次 |

## 2. 系统范围

本系统包含四个业务角色和六个主要功能域：

| 功能域 | 主要能力 | 主要角色 |
| --- | --- | --- |
| 账号与个人信息 | 登录、退出、修改密码、查看和维护个人信息、账号启停用 | 四类角色；账号管理由系统管理员负责 |
| 消息通知 | 公告、站内消息、业务状态通知、已读处理 | 四类角色 |
| 入宿基础管理 | 楼栋、宿舍、床位、学生住宿分配、住宿信息查询 | 学生、宿管、系统管理员 |
| 报修管理 | 报修、审核、派单、接单、维修、延期、确认、评价、重修、归档 | 四类角色 |
| 假期留宿 | 开放区间、申请、锁定、审核、重交、逾期补录、归档和统计 | 学生、宿管、系统管理员 |
| 系统通用管理 | 全局查询、统计、导入导出、操作日志、备份恢复 | 系统管理员为主 |

本阶段不把“架构设计、技术栈选型、数据库设计、包图、类图”写入用例说明。它们属于后续设计阶段。

## 3. 参与者定义

### 3.1 学生

学生是报修和假期留宿的申请方，也是维修结果确认和评价方。学生只能查看和操作自己的报修、留宿申请、住宿信息和消息。

### 3.2 宿管

宿管负责管辖楼栋范围内的业务审核和现场管理，包括报修审核、手动强制派单、异常工单处理、延期和重修审核、留宿申请锁定审核及楼栋数据查询。

### 3.3 维修人员

维修人员负责处理被派发的报修工单，包括自动派单后的接单或拒单、现场维修、延期申请和维修结果提交。维修人员不能审核留宿申请，也不能维护系统基础规则。

### 3.4 系统管理员

系统管理员负责系统级账号权限、宿舍基础数据、报修规则、维修人员能力范围、留宿开放区间、全校数据查询、系统消息和通用运维管理。

### 3.5 系统内部定时处理

系统内部的定时任务不是第五个业务角色，不在角色图中单独计入。它由系统根据时间条件自动执行，例如：

- 自动锁定留宿申请；
- 判断待修改申请是否逾期；
- 判断报修工单是否超时未处理或超时未修好；
- 已维修工单超过确认期限后自动确认；
- 留宿结束日期次日 0:00 自动完成并归档。

这些处理在用例说明的“触发器”和“异常/定时分支”中描述。

## 6. 用例说明

### UC-C01 登录系统

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 登录系统 |
| 用例编号 | UC-C01 |
| 主要参与者 | 学生、宿管、维修人员、系统管理员 |
| 目标 | 通过账号凭证进入与角色匹配的操作端 |
| 触发器 | 用户打开系统登录页面并提交登录信息 |
| 前置条件 | 用户账号已存在且处于启用状态 |
| 后置条件 | 系统建立登录会话，按角色展示可用菜单和数据范围 |

**基本流程**

1. 用户输入账号和密码。
2. 系统校验账号是否存在、是否启用以及密码是否正确。
3. 系统识别用户角色。
4. 系统创建登录会话并进入对应首页。
5. 系统记录必要的登录日志。

**备选和异常流程**

- 账号不存在、已禁用或密码错误时，系统拒绝登录并提示原因。
- 连续失败达到安全策略时，系统可以暂时限制继续尝试。
- 用户已登录时再次进入登录页，应回到已有会话或要求重新认证。

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 维护个人信息 |
| 用例编号 | UC-C02 |

| 前置条件 | 用户已登录 |
| 后置条件 | 合法修改保存，变更记录被保留 |

**基本流程**

1. 用户打开个人信息页面。

3. 用户修改允许维护的字段。
4. 系统校验字段格式和必填项。
5. 系统保存修改结果并刷新页面。

**业务规则**

- 用户不能通过个人信息页面修改角色、账号状态、负责楼栋或系统权限。
- 学生的宿舍、楼栋和床位由住宿基础数据决定，不能由学生自行修改。

### UC-R01 提交报修工单

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 提交报修工单 |
| 用例编号 | UC-R01 |
| 主要参与者 | 学生 |
| 目标 | 创建并提交宿舍故障维修申请 |
| 触发器 | 学生进入报修页面并选择新建或继续编辑工单 |
| 前置条件 | 学生已登录，存在有效住宿信息 |
| 后置条件 | 工单保存为“待审核”，宿管收到审核提醒 |

**基本流程**

1. 学生填写故障位置、故障类型、维修类型、故障描述和备注。
2. 学生按需上传故障图片。
3. 学生选择保存草稿或提交。
4. 保存草稿时，工单状态为“待编辑”。
5. 提交时，系统校验字段、图片和故障分类。
6. 校验通过后，系统保存本次提交版本，状态变为“待审核”。
7. 系统按照楼栋管辖关系通知宿管。

**备选和异常流程**

- 必填内容缺失或图片格式不符合要求时，不能提交。
- 学生在正式派单前可以撤销，工单进入“已撤销”，原记录保留。
- 宿管退回后，学生在“待修改”状态修改原工单并重新提交；超过配置期限未提交时，系统自动关闭并归档。

**业务规则**

- 工单被派单后，学生不能撤销。
- “已驳回”是审核结论，当前页面状态使用“待修改”。

### UC-R02 审核报修工单

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 审核报修工单 |
| 用例编号 | UC-R02 |
| 主要参与者 | 宿管 |
| 目标 | 判断报修是否属于校内维修范围并决定后续派单方式 |
| 触发器 | 宿管打开管辖楼栋的待审核工单 |
| 前置条件 | 宿管已登录，工单状态为“待审核” |
| 后置条件 | 审核通过后进入“待派单”；不通过后进入“待修改” |

**基本流程**

1. 宿管查看工单内容、故障分类、维修范围、图片和学生备注。
2. 宿管判断是否属于校内维修范围。
3. 符合范围时执行审核通过，工单进入“待派单”。
4. 宿管判断是否标记为紧急工单。
5. 普通工单进入自动派单池；紧急工单进入手动派单池。
6. 不符合范围时，宿管填写审核不通过原因。
7. 系统记录审核结论“已驳回”，当前状态改为“待修改”。
8. 系统通知学生修改并重新提交。

**异常流程**

- 审核不通过但未填写原因时，系统不允许提交审核结果。
- 重修工单也必须经过本用例，但审核通过后直接进入手动派单池。

### UC-R03 自动派单

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 自动派单 |
| 用例编号 | UC-R03 |
| 主要参与者 | 系统内部处理；系统管理员负责配置规则 |
| 目标 | 为普通报修工单选择尚未尝试且符合条件的维修人员 |
| 触发器 | 普通工单审核通过并进入自动派单池，或上一名维修人员拒单/超时未处理后回流 |
| 前置条件 | 工单状态为“待派单”或处于自动派单池；规则和人员基础数据有效 |
| 后置条件 | 成功时工单进入“待接单”；失败时进入待人工处理 |

**基本流程**

1. 系统读取工单的故障类型、维修类型、位置和紧急程度。
2. 系统按维修工种、故障类型和负责范围筛选维修人员。
3. 系统排除已经拒绝过该工单的维修人员。
4. 系统按当前工单数和负荷规则选择合适人员。
5. 系统生成派单记录并通知维修人员。
6. 工单状态变为“待接单”。

**异常和定时流程**

- 无匹配人员、所有人员负荷已满或已无新的合适人员时，工单进入“待人工处理”。
- 维修人员超过接单时限未接单且未拒单时，记录一次“超时未处理”。
- `拒单次数 + 超时未处理次数 <= 2` 且仍有未尝试人员时，工单重新进入自动派单池。
- `拒单次数 + 超时未处理次数 > 2` 时，工单标记为异常并进入手动派单池。
- 异常工单、紧急工单和重修工单不进入普通自动派单池。

### UC-R04 手动强制派单

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 手动强制派单 |
| 用例编号 | UC-R04 |
| 主要参与者 | 宿管 |
| 目标 | 为紧急、异常、重修或待人工处理工单指定合格维修人员 |
| 触发器 | 宿管打开手动派单池或待人工处理工单 |
| 前置条件 | 宿管有对应楼栋权限；工单需要手动派单 |
| 后置条件 | 派单成功后工单进入“已接单”，系统自动确认维修人员接单 |

**基本流程**

1. 宿管查看故障类型、维修范围、紧急程度和维修人员当前工单数。
2. 系统展示符合维修资质的维修人员。
3. 宿管选择维修人员并确认强制派单。
4. 系统生成手动派单记录并发送通知。
5. 系统自动确认维修人员接单。
6. 工单状态变为“已接单”。

**业务规则**

- 强制派单不产生拒单记录和超时未接单记录。
- 强制派单后仍需按维修时限判断超时未修好。
- 找不到合格人员时，工单保持待人工处理，由宿管或系统管理员协调人员、调整负责范围或按审核退回流程处理。

### UC-R05 处理自动派单

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 处理自动派单 |
| 用例编号 | UC-R05 |
| 主要参与者 | 维修人员 |
| 目标 | 对系统自动派发的工单进行查看、接单或拒单 |
| 触发器 | 维修人员收到自动派单通知 |
| 前置条件 | 派单记录有效，工单处于“待接单” |
| 后置条件 | 接单后工单进入“已接单”；拒单后系统记录原因并重新判定派单 |

2. 维修人员选择确认接单或拒绝接单。
3. 确认接单时，工单状态变为“已接单”。
4. 拒绝接单时，必须填写拒单原因。
5. 系统记录拒单次数和本次派单结果。
6. 系统根据异常规则决定重新自动派单、进入手动派单池或待人工处理。

**异常流程**

- 超过接单时限未操作时，系统记录超时未处理，不等同于拒单。
- 被宿管强制派单的工单不进入本用例，系统已自动确认接单。

### UC-R10 处理异常和无可派人员工单

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 处理异常和无可派人员工单 |
| 用例编号 | UC-R10 |
| 主要参与者 | 宿管、系统管理员 |
| 目标 | 处理系统无法按普通自动派单规则完成的工单 |
| 触发器 | 工单达到异常条件或进入待人工处理 |
| 前置条件 | 用户具有对应楼栋或全校管理权限 |
| 后置条件 | 工单被强制派单、重新进入派单池或按审核退回 |

**基本流程**

1. 宿管或系统管理员查看异常原因、拒单记录、超时记录和维修历史。
2. 判断工单属于异常工单、无匹配人员、负荷已满或无新的可派人员。

- 异常工单进入手动派单池，之后不再进入普通自动派单池。
- 强制派单后不再产生拒单和超时未接单记录，但仍计算超时未修好。

### UC-S05 审核留宿申请

| 项目 | 说明 |
| --- | --- |
| 用例名称 | 审核留宿申请 |
| 用例编号 | UC-S05 |
| 主要参与者 | 宿管 |
| 目标 | 审核管辖楼栋已锁定的留宿申请 |
| 触发器 | 宿管打开“审核中”申请 |
| 前置条件 | 申请已锁定，状态为“审核中” |
| 后置条件 | 通过时进入“已通过”；不通过时进入“待修改” |

**基本流程**

1. 宿管查看学生身份、留宿日期和申请内容。

- 宿管只能查看学生已经提交的版本，不能把学生未提交的草稿作为审核依据。

**统计规则**

- 留宿人数是审核通过以及审核截止后人工补录并审核通过的学生人数。
- 留宿人数不代表学生实际入住；本业务不处理提前离宿或延长留宿。
- 待审核、待修改和已归档申请可以进入申请历史统计，但只有审核通过的申请计入当前留宿人员。

## 7. 状态和权限基线

### 7.1 报修工单状态

| 状态 | 含义 |
| --- | --- |
| 待编辑 | 学生尚未提交的草稿 |
| 待审核 | 学生已经提交，等待宿管审核 |
| 待修改 | 审核不通过后等待学生修改并重新提交 |
| 待派单 | 审核通过，等待自动或手动派单 |
| 待接单 | 普通工单已经自动派给维修人员，等待接单、拒单或超时 |
| 已接单 | 维修人员已接单，或强制派单后系统自动确认 |
| 维修延期 | 延期申请审核中或延期已通过后的维修阶段 |
| 已维修 | 维修人员已提交维修结果和完工照片，等待学生确认 |
| 已确认 | 学生确认或系统超时自动确认 |
| 待人工处理 | 暂时无法完成自动或手动派单，需要人工介入 |
| 已关闭 | 待修改工单超过期限未重新提交 |
| 已撤销 | 学生在允许阶段撤销工单 |
| 已归档 | 业务完成后进入历史记录 |

“异常工单”是独立标记，不替代上述状态。“已驳回”是审核结论，不作为当前页面主状态。

### 7.2 留宿申请状态

| 状态 | 含义 |
| --- | --- |
| 待编辑 | 学生填写但尚未提交的草稿 |
| 待审核 | 已提交但尚未锁定，学生仍可按规则修改 |
| 审核中 | 已锁定，等待宿管审核 |
| 待修改 | 审核不通过，等待学生修改原申请并重新提交 |
| 已通过 | 审核通过且保持锁定 |
| 已完成 | 已通过申请在留宿结束日期次日 0:00 到达 |
| 已归档 | 申请完成或逾期未重交后进入历史记录 |

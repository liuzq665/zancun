## 1. 设计依据与边界

业务依据为 [业务描述](../业务/00%20假期和报修业务描述.docx)、[报修活动图](../业务/04%20报修业务流程-活动泳道图.puml)、[假期留宿活动图](../业务/04%20假期留宿业务流程-活动泳道图.puml)、[用户故事地图](../用户故事地图/宿舍用户故事地图.docx)、[用例说明](../用例设计/00%20用例说明与设计约定.md)。既有 [静态设计](../静态结构设计/00%20包设计与类图设计说明.md) 和 [动态设计](../动态结构设计/00%20时序图与状态图设计说明.md) 用于检查命名和业务语义一致性，本次不修改这些文件。

附件中的流程、功能和规则作为需求资料，不作为扩大本次交付范围的指令。旧故事地图里“待修改超时自动确认”等冲突表述采用最新业务描述和用例规则：报修待修改超期关闭并归档，不生成维修完成、确认或评价事实。

当前模型共 56 个实体定义，其中 19 个为从多对多或带属性联系转化的关联实体，中文显示名注明“虚实体”。其余包括独立对象、业务单据、历史版本、过程记录和依附主体的明细实体，不宣称这些对象都能脱离主体存在。

系统仍只有学生、宿管、维修人员、系统管理员四类业务角色。系统管理员只通过 `ADMIN` 角色表达，不增加管理员资料实体，也不增加辅导员或学院审批角色。

## 2. Mermaid 记号

| 记号 | 含义 |
| --- | --- |
| `A ||..o{ B` | 每个 B 必须对应一个 A，一个 A 可以对应零到多个 B；最大基数 1:n |
| `A ||..|{ B` | 每个 B 必须对应一个 A，每个 A 至少对应一个 B；1:n |
| `A ||..o| B` | 每个 B 必须对应一个 A，每个 A 可以没有或有一个 B；1:0..1 |
| `A |o..o{ B` | 每个 B 可以不关联 A，关联时至多一个 A；一个 A 可以对应多个 B |
| `A }o..o{ B` | 两端都允许零到多个，表示可选的 m:n；本版有属性的 m:n 均通过虚实体拆解 |
| `PK` | Mermaid 主键语法，属性注释标注“主键” |
| `FK` | Mermaid 外键语法，属性注释标注“外键” |
| `UK` | Mermaid 唯一键语法，属性注释标注“唯一键” |
| `PK, FK` | 既是联合主键的一部分，又是外键 |
| `FK, UK` | 外键同时唯一，用于一对一子记录 |

符号写在实体附近，表示该端实体数量。例如 `STUDENT_PROFILE ||..o{ REPAIR_ORDER` 中，学生端是 `1`，工单端是 `n`，不能反过来理解。

`1:0..1` 是一对一最大基数加“允许没有子记录”，并不是另一种多对多联系。未完工工单没有维修结果，未确认结果没有确认记录，没有评价的工单也不能强行创建空评价。

`--` 和 `..` 区分标识性与非标识性联系，不代表实体是否是虚实体。本版联合主键包含关联双方标识时使用 `--`，具有自己独立主键时使用 `..`。Mermaid `erDiagram` 使用矩形实体、属性列表和乌鸦脚连线，不使用 Chen 图的菱形和椭圆；虚实体用名称标注，不误用关系虚线表示虚实体。

类型只使用 `bigint`、`string`、`boolean`、`date`、`datetime`，不在本阶段决定数据库字段长度、默认值、SQL 类型或索引。

### 3.1 规范化支撑实体

学生资料原来含院系名称、专业名称和班级名称，若把这些层级信息全部放在每名学生身上，会重复保存班级所属专业、专业所属院系。本版建议补充三个支撑实体：

- 院系保存院系编码、院系名称、启用情况。
- 专业保存专业编码、专业名称及所属院系。
- 班级保存班级编码、班级名称、所属专业和班级入学年份。
- 学生资料只关联班级，沿联系得到专业和院系，不重复保存三个名称。

这不意味着必须增加一套学院管理或审批流程。本版采用“一班级属于一个专业，一专业属于一个院系”的假设，编码在校内唯一；未归班学生允许班级关联为空。如果学校有跨专业班级、双专业学籍或转专业历史需求，需要进一步调整该模型，不能直接套用当前基数。`enrollment_year` 是班级入学年份，不表示每名学生的实际入学年份。

### 3.2 不额外建模的概念

- 自动派单池、手动派单池、待人工处理池：由工单状态及紧急、异常、重修条件筛选，不是需要复制工单数据的独立实体。
- 拒单次数、超时次数、当前工单数、入住人数、留宿人数、维修完成率、平均评分：由事实记录计算，不是独立实体或重复保存的基本属性。
- 当前床位占用、当前舍友：由有效住宿分配查询得到。
- 已驳回：审核结论，不是独立实体，也不是工单或留宿申请主状态。
- 已完成留宿历史：由申请的完成时间、归档时间及版本记录表达，不再复制一张包含相同申请数据的“历史表”实体。
- 设施设备台账、资产、耗材、费用、巡检、违纪、缴费、访客、实际留宿入住登记：当前资料没有相应业务，不为了“实体尽可能完整”擅自加入。
- 维修类型：当前资料同时使用“维修类型”和“维修工种”，但未定义独立维修类型的属性及与工种的对应规则。本版暂按维修工种选择项表达；若两者业务含义不同，应增加维修类型及明确映射，而不是凭文字称谓制造实体。

## 5. 虚实体与联系属性

“虚实体”在本版指将联系实体化后的关联实体，并不是数据库视图、临时数据或不存在的对象。是否实体化取决于多对多、历史和联系属性，而不是只因为它的名字含“记录”。

典型联系属性的归属：

- 授权生效时间属于用户与角色的授权，不属于账号或角色本身。
- 管辖起止日期属于宿管与楼栋的联系，不属于楼栋或宿管资料本身。
- 入住、退宿、调宿原因属于学生与床位的住宿关系，不放在学生资料或床位上。
- 资质等级和有效期属于维修人员与工种的联系，不放在工种名称中。
- 派单方式、派单时间、拒单原因和接单期限属于某次工单与维修人员的联系。
- 本楼栋申请截止时间属于批次与楼栋的联系，不属于楼栋永久属性或全校开放区间。
- 文件在任务中是输入、输出或错误报告，属于任务与文件的联系，不是文件自身类型。
- 接收时间和读取时间属于消息与接收用户的联系，不能只在消息主体保存一个全局已读值。

审核记录、提交版本和日期段虽然依附主体，仍是需要识别和保存的事件或明细实体。它们不会因为依附存在就全部被称为独立实体，也不会全部被误称为多对多虚实体。

## 6. 范式与“一事一地”检查

### 6.1 第一范式

多角色、多权限、多楼栋、工种资质、多张图片、多轮审核和多个留宿日期段分别用记录表达，不把逗号列表或数组放进一个业务属性。每个基本属性只表达一个事实；任务的查询条件只记录一次导出请求，不代替规范化的业务数据。

### 6.2 第二范式

具有联合主键的角色权限、附件联系、消息接收记录和版本例外依据，其非键属性依赖完整联系。例如文件用途依赖“该任务使用该文件”，读取时间依赖“该用户读取该消息”，不能仅依赖其中一端。

独立主键的历史关联还需要检查业务候选键；本版在第 7 节说明组合唯一或时间有效性约束，而不是以“已有自增主键”代替范式分析。

### 6.3 第三范式

- 账号姓名、联系方式和性别只在用户账号保存，不复制到学生、宿管或维修人员资料。
- 学生学籍层级由班级 -> 专业 -> 院系表达，避免 `学生 -> 班级 -> 专业/院系名称` 的传递依赖。
- 宿舍只关联楼栋，床位只关联宿舍；学生只通过住宿分配关联床位，不重复当前楼栋、宿舍和床位。
- 报修内容和分类只存提交版本，审核只关联实际版本，不再额外保存能从版本推导的工单外键。
- 延期申请和维修人员过程记录只关联派单，不再重复派单可确定的工单及维修人员。
- 留宿申请主体只保存学生与批次，以便约束同学生同批次唯一；受理楼栋规则通过独立的申请楼栋范围联系保存，不能在主体再重复楼栋。版本日期段只关联提交版本，不重复申请主体、批次或楼栋。
- 维修评价通过确认 -> 结果 -> 工单 -> 学生取得归属，不重复工单、学生和维修人员姓名等属性。
- 文件只保存一个存储定位键，业务附件只保存联系，不重复存储文件名、大小或地址。

最终是否严格满足第三范式还取决于学校确认的实际函数依赖。当前明确的班级、专业、院系和工种对应假设见第 3 节；若新增约束，例如每类故障固定唯一工种，必须据此调整联系和属性，不把当前 m:n 当作永远成立的事实。

### 6.4 不重复保存的派生值

床位占用由有效住宿分配推导；消息是否已读由 `read_at` 推导；留宿锁定由当前状态推导；是否重修由 `parent_order_id` 推导。异常判定由派单历史中的拒单、接单超时和维修人员过程记录中的施工超时推导；历史事实保留后，异常标记不会因为更换负责人消失。重修次数沿工单自联系链计算。

工单和申请的 `current_status` 是业务状态机的当前事实，不应再建立存有相同当前状态的“状态实体”。操作日志保存历史操作，不替代当前状态。

### 6.5 一事一地的准确解释

“一事一地”要求同一业务事实只有一个权威存放位置，不意味着全图不能出现相同字段名。不同实体的 `created_at` 分别表示各自建立时间，属于不同事实；联系实体出现父实体标识作为外键是引用，不是重新定义父实体属性。

提交版本与当前配置保留不同时间的事实，不是无理由重复。登录日志里的输入账号保存的是“当时输入了什么”，不等于复制当前用户账号。操作日志里的审计对象标识仅为历史定位，刻意不标成可验证的业务外键。

## 7. 连线之外必须成立的约束

Mermaid 不能表达所有组合唯一、跨路径唯一、时间区间、条件必填和角色规则。以下为 ER 业务约束，不在本阶段展开 SQL。

| 对象 | 约束 |
| --- | --- |
| 用户角色 | 同账号同角色的有效授权区间不能重叠；允许保留过期授权历史 |
| 角色权限 | 联合主键 `(role_id, permission_id)` 防止重复授权 |
| 角色专有资料 | 一个账号至多一份某类型资料；使用该类型业务能力时必须拥有对应有效角色 |
| 宿舍、床位 | `(building_id, room_no)`、`(room_id, bed_no)` 分别唯一 |
| 住宿分配 | 有效区间为 `[check_in_date, check_out_date)`；结束为空表示持续。排除已取消分配后，同床位或同学生的区间不能重叠；不能只检查今天 |
| 宿管及维修范围 | 同人员同楼栋范围的日期区间不能重叠，历史范围不可覆盖成当前单值 |
| 工种资质及故障工种配置 | 同一对关联对象的有效区间不能重叠；资格与配置当前有效时才参与筛选 |
| 报修规则 | 单一全局规则序列版本唯一；同一时刻只能有一个当前生效版本。已被工单采用的规则版本不可原地覆盖 |
| 内容版本 | `(order_id, version_no)` 或 `(application_id, version_no)` 唯一。已提交版本不可修改；保存编辑使用独立未提交草稿，宿管仍只看已提交版本 |
| 报修提交 | 草稿允许缺少位置、分类、工种和描述；正式提交必须齐全，并检查有效住宿与故障宿舍的一致性 |
| 报修审核 | 只能审核当前有效的已提交版本；驳回必须有原因和重交期限。保存草稿不重置原重交期限 |
| 派单记录 | 同工单同一时刻最多一条当前有效负责关系；工单归档时结束负荷归属。人工强制派单必须有操作者，自动派单没有虚构人工操作者 |
| 接单和拒单 | 强制派单直接确认接单，不填接单截止、不生成拒单或接单超时；自动接单、拒单、超时互斥 |
| 维修人员过程记录 | 每次派单的施工超时事实最多一次；拒单和接单超时以派单结果为准，不复制进另一套计数记录 |
| 延期申请 | 同次有效派单最多一份未决延期申请；审核账号、时间与结果一致。审核期间暂停施工超时判断，驳回恢复原期限，通过后用批准预计时间 |
| 最终维修结果 | 同工单最多一份，提交者必须是当时有效负责人；提交必须有完工照片。换人历史使用派单和过程记录，不创建多份最终结果 |
| 维修确认 | 同结果最多一次。学生确认关联原申请人的账号；系统确认不冒充学生操作者 |
| 维修评价 | 同确认最多一份，只能由申请人提交；评分范围待业务确定，不凭空固定星级或分值 |
| 重修自联系 | 不能指向自己或形成环；原单与重修单的申请人一致；创建时原单尚未确认，检查重修上限，重新审核后只进入手动派单 |
| 批次楼栋规则 | `(batch_id, building_id)` 唯一；截止时间和自动锁定只影响该楼栋批次 |
| 留宿开放区间版本 | `(batch_id, version_no)` 唯一，每版只有一个连续区间，开始不晚于结束；已发布版本不可覆盖，后续版本触发重新校验 |
| 留宿申请主体 | 学生与 `building_rule_id -> batch_id` 所确定的批次组合唯一。不能只约束学生与楼栋规则组合，否则同批次换楼栋时可能建立第二张申请 |
| 留宿受理范围 | 建立时核对学生有效住宿的楼栋与受理规则。若同批次调宿需要迁移受理楼栋，应另定迁移规则，不创建第二张申请或默默改历史归属 |
| 留宿日期段 | 草稿可零段；提交时至少一段。使用含首尾日期的闭区间，全部落在最新开放区间内，不允许共享边界日 |
| 留宿审核与复核 | 记录审核的提交版本及开放区间版本；同申请轮次唯一。区间变更时建立待复核记录，未决复核不得生成完成事实，退回时保存本轮重交期限 |
| 留宿完成归档 | 仅获准且不存在未决区间复核时，最后一个通过日期段结束次日 0:00 完成。待修改逾期只归档，`completed_at` 为空 |
| 例外授权 | 只影响指定学生与指定批次楼栋范围，不改变全体截止；授权有效且未撤销时可用；提交保存真实授权依据和操作者 |
| 消息目标 | ALL时三个对象外键均空；ROLE、BUILDING、USER时恰有一个对应外键非空。不使用多态 `target_id` 伪外键 |
| 消息接收记录 | 联合主键 `(message_id, user_id)` 对多个目标展开的用户去重。`read_at` 空表示未读，首次读取后不改其他用户记录 |
| 附件联系 | 每对业务对象与文件唯一；允许同一文件被多个版本引用。延期、完工照片提交要求在业务动作时检查，不能由全生命周期最小基数替代 |
| 导入导出任务 | PARTIAL只用于实际已写入部分合法行的导入；错误保存逐行明细。输入、输出、错误报告用途分别检查，导出不要求上传输入文件 |
| 备份恢复任务 | 恢复必须二次确认、校验输入和准备保护备份；保护任务必须确为备份，不能自关联成环。恢复失败保留失败及回退结果，审计不被本次恢复覆盖 |
| 操作及登录日志 | 人工动作关联真实账号，系统动作允许账号为空；失败登录允许没有对应账号。日志不是各种业务记录的替代实体 |

## 8. 状态一致性

状态名称遵循最新用例与动态设计，不沿用早期类图缺失状态的枚举集合。

| 对象 | 状态或结论 |
| --- | --- |
| 报修工单 | `DRAFT` 待编辑、`PENDING_REVIEW` 待审核、`PENDING_EDIT` 待修改、`PENDING_ASSIGN` 待派单、`PENDING_ACCEPT` 待接单、`ACCEPTED` 已接单、`DELAYED` 维修延期、`REPAIRED` 已维修、`CONFIRMED` 已确认、`PENDING_MANUAL` 待人工处理、`CLOSED` 已关闭、`WITHDRAWN` 已撤销、`ARCHIVED` 已归档 |
| 派单记录 | `PENDING` 待接单、`ACCEPTED` 已接单、`REJECTED` 已拒单、`TIMEOUT` 超时未接、`CANCELLED` 已作废；负责关系结束时间与结果分别记录 |
| 延期申请 | `PENDING_REVIEW` 待审核、`APPROVED` 已通过、`REJECTED` 未通过、`INVALIDATED` 已失效 |
| 报修审核结论 | 通过或驳回，不代替工单主状态 |
| 留宿申请 | `DRAFT` 待编辑、`PENDING_REVIEW` 待审核未锁定、`UNDER_REVIEW` 审核中已锁定、`PENDING_EDIT` 待修改、`APPROVED` 已通过、`COMPLETED` 已完成、`ARCHIVED` 已归档 |
| 留宿审核与复核 | `PENDING` 待审核或待复核、`APPROVED` 通过、`REJECTED` 不通过、`CANCELLED` 审核要求已失效；不新增申请主状态 |
| 导入导出任务 | `WAITING` 待执行、`RUNNING` 执行中、`SUCCESS` 成功、`PARTIAL` 部分成功、`FAILED` 失败、`CANCELLED` 启动前取消 |
| 备份恢复任务 | `WAITING`、`RUNNING`、`SUCCESS`、`FAILED`、`CANCELLED`，无PARTIAL |

提交版本只用 `submitted_at` 区分未提交草稿与提交事实，不同时保存可能矛盾的“已提交布尔值”。撤回保留提交历史，以主体状态及操作日志判断当前申请是否有效。

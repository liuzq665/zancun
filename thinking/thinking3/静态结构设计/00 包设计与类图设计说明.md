## 1. 设计范围

本设计描述系统的静态结构，不展开数据库表、SQL、接口参数和页面布局。类图中的持久化领域类与 ER 图中的实体基本对应，但二者不是完全等价关系：

- ER 图描述业务数据实体、联系和基数。
- 类图描述程序中的对象、职责、方法、继承和依赖。
- 多对多联系、历史版本、审核记录、派单记录等在程序中建模为独立领域类。
- 外键不在领域类中重复堆叠为数据库字段；对象关联通过属性类型和关联线表达，具体 Mapper 字段映射留到数据库实现阶段。
- `bigint`、`string`、`boolean`、`date`、`datetime` 是 ER/数据模型类型；类图使用 Java 类型 `Long`、`String`、`Boolean`、`LocalDate`、`LocalDateTime`。

四类角色不分别复制一套业务类。当前采用“用户账号 + 角色 + 权限 + 角色专有资料”的设计：学生、宿管、维修人员通过角色和对应资料类组合得到，系统管理员暂通过 `Role=ADMIN` 表达，不单独建立管理员资料类。后续如果出现管理员专有属性或独立业务行为，再补充 `AdminProfile` 或管理员领域类。

## 2. 包设计原则

### 2.1 总体包结构

根包为 `com.dorm.mis`，采用“业务域分包 + 域内分层”的方式：

├── job                            # 定时任务和自动状态处理
├── auth                           # 账号、角色、权限和人员资料
│   ├── controller
│   ├── service
│   ├── dto
│   ├── vo
│   ├── entity
│   └── mapper
├── dorm                           # 楼栋、宿舍、床位和住宿分配
│   ├── controller
│   ├── service
│   ├── dto
│   ├── vo
│   ├── entity
│   └── mapper
├── repair                         # 报修配置和工单全流程
│   ├── controller
│   ├── service
│   ├── dto

│   ├── entity

│   ├── service

### 2.2 各包职责

| 包 | 主要职责 | 可以依赖 | 不应承担的职责 |
| --- | --- | --- | --- |
| `common` | 统一响应、分页、业务异常、枚举基础接口、工具 | JDK、基础库 | 具体报修或留宿规则 |
| `config` | Spring、MyBatis、Jackson、跨域、文件存储配置 | Spring、common | 编写业务流程 |
| `security` | JWT、认证过滤、当前用户、角色权限、数据范围 | auth、common、Spring Security | 修改报修或住宿数据 |
| `controller` | 接收请求、校验 DTO、调用 Service、返回 VO | 本域 service、dto、vo、common | 直接访问 Mapper、直接控制事务 |
| `service` | 业务编排、状态流转、事务、权限和领域规则调用 | 本域 entity/rule、mapper、相关域 service、common | 拼接 HTTP 响应细节、编写页面逻辑 |
| `entity` | 领域对象、状态和生命周期数据 | JDK、基础注解 | 接收 HTTP DTO、发起数据库查询 |
| `rule` | 可复用的报修/留宿判定策略 | entity、common | 直接写 Controller 或数据库 SQL |
| `mapper` | 数据查询、保存、分页和统计 SQL 映射 | 本域 entity、MyBatis | 实现跨步骤业务流程 |
| `file` | 文件元数据和文件存储适配 | common、file entity、存储 SDK | 把文件路径硬编码到业务实体 |
| `job` | 超时扫描、自动确认、自动锁定、归档 | 相关 service | 绕过 Service 直接改 Mapper |
| `statistics` | 跨模块统计和报表组装 | 各域 service/mapper、VO | 修改业务状态 |

### 2.3 包之间的依赖规则

1. `controller -> service -> mapper` 是请求处理的主方向。
2. `controller` 不得直接依赖 `mapper`。
3. `service` 可以依赖本域实体和必要的跨域服务，但跨域调用必须通过公开 Service 接口，不能读取对方 Mapper 的内部实现。
4. `mapper` 只负责持久化，不能反向依赖 Controller 或 Job。
5. `job` 只能调用 Service 的公开方法；自动处理和人工处理必须复用同一套状态规则。
6. `security` 提供当前账号和权限判断能力，业务 Service 负责进一步执行数据范围校验。
7. `dto`/`vo` 只位于接口边界；领域实体不能继承 DTO 或 VO。
8. `file` 通过 `FileStorage` 接口隔离本地目录和 MinIO，业务域只依赖 `FileService`；业务对象与文件资源的归属通过各业务域的明确联系保存，不使用通用多态 `ownerType + ownerId` 绑定。
9. `statistics` 作为查询侧包，禁止反向改变业务实体状态。
10. 模块之间禁止形成环形依赖；例如 `notice` 可被 `repair`、`stay` 调用，但 `notice` 不反向依赖报修或留宿实体。

## 3. 业务域包设计

### 3.1 `auth` 账号权限包

- 领域类：`SysUser`、`Role`、`Permission`、`UserRole`、`RolePermission`、`StudentProfile`、`DormManagerProfile`、`RepairerProfile`。
- Service：登录、改密、账号启停用、角色权限分配、人员资料维护、数据范围判断。
- 约束：角色权限是配置数据；学生、宿管、维修人员资料与账号一对一可选关联，不把楼栋、床位、工种直接塞入用户账号。

### 3.2 `dorm` 住宿基础包

- 领域类：`Building`、`DormRoom`、`Bed`、`AccommodationAssignment`、`DormManagerBuildingScope`。
- Service：楼栋/宿舍/床位维护、住宿分配、退宿、历史查询、管辖范围查询。
- 约束：当前床位占用由有效住宿分配计算，`Bed` 只保存床位自身管理状态；宿舍所属楼栋通过对象关联表示。

### 3.3 `repair` 报修包

- 配置类：`FaultCategory`、`RepairWorkType`、`RepairRule`、`FaultWorkTypeConfig`、`RepairerWorkTypeQualification`、`RepairerBuildingScope`。
- 流程类：`RepairOrder`、`RepairSubmissionVersion`、`RepairAuditRecord`、`DispatchRecord`、`RepairDelayApplication`、`RepairResult`、`RepairConfirmation`、`RepairEvaluation`、`WorkOrderExceptionRecord`。
- Service：提交、审核、自动/手动派单、接单/拒单、维修、延期、确认、评价、重修、异常处理和统计查询。
- 约束：工单状态只能由 Service 按状态机推进；拒单、超时、延期和重修均保留过程记录，不能只覆盖工单当前状态。

### 3.4 `stay` 假期留宿包

- 领域类：`StayBatch`、`StayBatchBuildingRule`、`StayApplication`、`StaySubmissionVersion`、`StayDateRange`、`StayReviewRecord`。
- Service：配置开放区间、发布批次、提交/修改/撤销、锁定、审核、逾期补录、归档和统计。
- 约束：日期段是提交版本的多值事实，单独建类；批次对不同楼栋的截止和锁定规则通过 `StayBatchBuildingRule` 表达。

### 3.5 `notice`、`file` 和 `system` 通用包

- `notice`：`SiteMessage`、`MessageTarget`、`MessageReceipt`，处理发布范围、接收生成和已读状态。
- `file`：`FileResource` 和 `FileStorage`，统一处理报修图片、现场照片、消息附件、导入导出文件和备份文件。
- `system`：`LoginLog`、`ImportExportTask`、`ImportErrorDetail`、`BackupTask`、`OperationLog`，提供审计、批处理和备份能力。

## 4. 核心类设计约定

### 4.1 领域类

领域类主要保存身份、状态、时间、业务数据和对象关联。简单状态变化可提供领域方法，例如 `RepairOrder.markUrgent()`；涉及权限、多个实体或事务的操作放到 Service，不把完整流程塞进 Entity。

### 4.2 Service 类

Service 方法以业务用例命名，并在方法边界处理事务和幂等：

| Service | 核心方法 | 主要事务边界 |
| --- | --- | --- |
| `AuthService` | `login`、`changePassword`、`assignRole` | 登录日志与会话结果 |
| `DormService` | `assignBed`、`terminateAssignment`、`queryAccommodation` | 检查床位冲突并保存住宿分配 |
| `RepairOrderService` | `submit`、`audit`、`dispatch`、`accept`、`complete`、`confirm`、`evaluate`、`requestRework` | 工单状态、过程记录、消息和文件关联 |
| `StayApplicationService` | `submit`、`lock`、`audit`、`resubmit`、`archive` | 版本、日期段、审核结果和状态同步 |
| `NoticeService` | `publish`、`generateReceipts`、`markRead` | 消息目标解析与接收记录生成 |
| `SystemTaskService` | `importData`、`exportData`、`backup`、`restore` | 任务、错误明细、文件和审计记录 |

### 4.3 Mapper 类

每个 Mapper 以一个聚合根或查询对象为中心，如 `RepairOrderMapper`、`StayApplicationMapper`、`BuildingMapper`。复杂报表可以放在 `statistics` 查询 Mapper，但不能将状态机判断下沉到 Mapper。

## 6. 与 ER 图的对应关系

| ER 模型对象 | 程序类设计 |
| --- | --- |
| 独立实体 | 通常对应一个 `entity` 类 |
| 多对多联系 | 对应关联实体类，如 `UserRole`、`RolePermission`、`AccommodationAssignment` |
| 带历史/过程属性的联系 | 对应过程类，如 `DispatchRecord`、`RepairAuditRecord`、`StayReviewRecord` |
| 文件资源 | 统一对应 `FileResource`，业务类通过关联使用，不重复文件地址 |
| 联系基数 | 在类图关联线上表达，在 Service 中通过校验落实 |
| 操作日志的多态对象 | 保留 `objectType + objectId` 审计字段，不把日志强行关联到所有业务类 |

- [x] 多对多关系均有明确的关联类。
- [x] 文件资源、消息接收记录、导入错误明细等系统通用对象已纳入。

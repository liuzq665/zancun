## 1. 设计目标

本阶段在用例图和用例说明之后，确定系统整体架构、技术栈、分层方案、部署形态和工程协作方式，为后续数据库设计、包图、类图和接口设计提供技术边界。

系统面向四类角色：学生、宿管、维修人员、系统管理员。四类角色分别拥有自己的操作端或功能视图，但业务数据统一由后端服务管理，避免多端数据割裂。

## 2. 架构结论

系统建议采用 **B/S 架构 + 前后端分离 + Spring Boot 单体分层架构** 作为课程设计阶段的主架构。

选择理由：

1. 宿舍系统业务模块较多，但规模仍适合单体应用，报修、留宿、账号、消息、住宿基础数据之间存在较强事务和权限关联。
2. Spring Boot + MyBatis 是 JavaWeb 项目常用组合，适合课程设计、团队开发和后续接口扩展。
3. 前后端分离便于学生端、宿管端、维修端、管理员端按角色组织页面，也便于后续扩展移动端或 H5。
4. 使用 Maven 统一管理依赖和构建，使用 Git 管理版本，使用 JUnit 做核心业务测试。
5. 部署上先支持 Docker Compose，本地和测试环境易运行；后续如需要课程展示 Kubernetes，可在容器化基础上扩展 K8s 部署。

## 4. 总体架构设计

### 4.1 架构形态

系统采用前后端分离架构：

- 前端：按角色提供学生端、宿管端、维修人员端、系统管理员端功能视图。
- 后端：统一提供 REST API，集中处理认证授权、业务规则、状态流转、数据访问和定时任务。
- 数据层：使用关系型数据库保存账号、住宿、报修、留宿、消息、日志等业务数据。
- 文件存储：保存报修故障图片、维修完工照片、延期现场照片、导入导出文件等。
- 部署层：优先 Docker 容器化，后续可扩展至 Kubernetes。

### 4.2 系统访问链路

1. 用户通过浏览器访问对应角色操作端。
2. 前端通过 HTTPS/HTTP 调用后端 REST API。
3. 后端通过 JWT 或 Session 机制识别当前登录用户。
4. 权限过滤器判断用户角色和数据范围。
5. Controller 接收请求并进行参数校验。
6. Service 执行业务规则、状态流转和事务控制。
7. Mapper 访问数据库，保存或读取业务数据。
8. 后端返回统一响应结构给前端。
9. 前端根据角色权限展示菜单、按钮和业务数据。

### 4.3 四端划分

四个角色可以共用一个前端工程，通过登录角色控制菜单和路由，也可以在页面上形成四套操作端：

| 操作端 | 主要用户 | 核心功能 |
| --- | --- | --- |
| 学生端 | 学生 | 查看住宿信息、提交报修、确认维修、评价、提交留宿申请、查看消息 |
| 宿管端 | 宿管 | 管辖楼栋查询、报修审核、手动派单、异常工单处理、留宿审核、楼栋消息 |
| 维修人员端 | 维修人员 | 查看派单、接单/拒单、提交维修结果、申请延期、查看个人记录 |
| 系统管理员端 | 系统管理员 | 账号权限、楼栋宿舍床位、报修规则、留宿开放区间、全校统计、日志备份 |

课程设计阶段建议采用 **一个前端工程 + 基于角色的路由菜单**，减少重复开发量。

## 6. 后端分层方案

后端采用典型 JavaWeb 分层结构：

| 层级 | 职责 | 典型内容 |
| --- | --- | --- |
| Controller 层 | 接收请求、参数校验、调用 Service、返回统一结果 | AuthController、RepairController、StayController |
| DTO/VO 层 | 请求参数和响应对象 | LoginDTO、RepairOrderCreateDTO、RepairOrderVO |
| Service 层 | 编排业务流程、处理状态流转、事务控制 | RepairOrderService、StayApplicationService |
| Domain/Entity 层 | 业务实体和状态枚举 | SysUser、RepairOrder、StayApplication |
| Mapper 层 | 数据访问、SQL 映射 | RepairOrderMapper、StayApplicationMapper |
| Job 层 | 定时任务和自动状态处理 | RepairTimeoutJob、StayArchiveJob |
| Config 层 | 安全、跨域、MyBatis、序列化等配置 | SecurityConfig、MybatisConfig |
| Common 层 | 统一响应、异常、分页、工具类 | Result、PageResult、BizException |

### 6.1 Controller 层约定

Controller 只做三件事：

1. 接收请求并完成基本参数校验。
2. 调用 Service 层方法。
3. 返回统一响应结构。

Controller 不直接写业务状态流转，不直接访问 Mapper，不直接处理事务。

### 6.2 Service 层约定

Service 是业务核心，负责：

- 报修提交、审核、派单、接单、延期、确认、评价、重修。
- 留宿申请、锁定、审核、重新提交、归档、统计。
- 权限数据范围校验，例如宿管只能处理管辖楼栋数据。
- 事务控制，例如审核通过并生成派单记录必须同事务完成。
- 业务异常抛出，例如状态不允许流转、超出重修上限、申请时间不在开放区间。

### 6.3 Mapper 层约定

Mapper 只负责数据访问：

- 单表增删改查。
- 必要的分页查询。
- 必要的统计查询。
- 不编写复杂业务状态判断。

### 6.4 Job 层约定

定时任务负责系统自动触发的业务处理：

| 定时任务 | 触发条件 | 处理内容 |
| --- | --- | --- |
| 报修接单超时扫描 | 派单后超过未接单时限 | 记录超时未处理，回流派单或进入异常 |
| 报修维修超时扫描 | 接单后超过维修完成时限 | 记录超时未修好，标记异常并进入手动派单池 |
| 报修自动确认扫描 | 已维修超过学生确认期限 | 自动确认维修完成并归档 |
| 待修改工单关闭扫描 | 待修改超过重新提交期限 | 自动关闭并归档 |
| 留宿自动锁定任务 | 申请截止时间到达且启用自动锁定 | 将申请锁定并进入审核中 |
| 留宿归档任务 | 留宿结束日期次日 0:00 | 标记已完成并归档 |

## 7. 业务模块划分

### 7.1 账号权限模块

负责登录、退出、修改密码、账号增删改查、角色权限和数据范围控制。

核心对象：用户、角色、权限、宿管负责楼栋关系。

### 7.2 入宿基础模块

负责楼栋、宿舍、床位、学生住宿分配和住宿信息查询。

核心对象：楼栋、宿舍、床位、入住记录。

### 7.3 消息通知模块

负责系统消息、业务消息、楼栋通知、已读未读状态。

核心对象：消息、消息接收人、消息类型。

### 7.4 报修模块

负责报修工单全流程。

核心功能：

- 学生提交报修。
- 宿管审核和标记紧急。
- 系统自动派单。
- 宿管手动强制派单。
- 维修人员接单、拒单、维修、延期。
- 学生确认、评价、申请重修。
- 异常工单和无可派人员处理。
- 报修规则配置和统计查询。

### 7.5 假期留宿模块

负责假期留宿申请全流程。

核心功能：

- 系统管理员配置连续开放区间。
- 宿管发布批次、设置截止时间和锁定规则。
- 学生提交留宿申请。
- 宿管锁定和审核。
- 学生修改并重新提交。
- 逾期补录和人工添加。
- 留宿完成归档和统计。

### 7.6 系统通用模块

负责操作日志、导入导出、备份恢复、系统配置。

## 8. 权限与认证设计

### 8.1 认证方式

建议采用 JWT Token：

1. 用户登录成功后，后端签发 Token。
2. 前端将 Token 放入请求头 `Authorization: Bearer <token>`。
3. 后端过滤器解析 Token，获取用户 ID、角色和权限。
4. 接口执行前判断是否拥有访问权限。

### 8.2 权限控制方式

权限控制分为两层：

| 层级 | 说明 | 示例 |
| --- | --- | --- |
| 功能权限 | 判断是否可以访问某个接口或菜单 | 维修人员不能审核留宿申请 |
| 数据权限 | 判断是否可以访问某条数据 | 宿管只能查看管辖楼栋工单 |

### 8.3 角色数据范围

| 角色 | 数据范围 |
| --- | --- |
| 学生 | 本人数据 |
| 宿管 | 管辖楼栋数据 |
| 维修人员 | 被派给自己的工单和本人维修记录 |
| 系统管理员 | 全校数据 |

## 9. 事务与一致性设计

以下操作必须使用事务：

| 操作 | 事务内容 |
| --- | --- |
| 报修提交 | 保存工单、保存图片关联、生成通知 |
| 报修审核通过 | 更新工单状态、写审核记录、进入派单池 |
| 自动派单 | 选择维修人员、生成派单记录、更新工单状态、发送通知 |
| 手动强制派单 | 生成派单记录、自动确认接单、更新工单状态、发送通知 |
| 维修完成 | 保存维修结果、保存完工照片、更新状态、通知学生 |
| 学生确认评价 | 更新确认状态、保存评价、归档工单 |
| 留宿提交 | 保存申请版本、更新状态、发送通知 |
| 留宿审核 | 更新审核结果、锁定状态、通知学生 |
| 留宿归档 | 更新生命周期状态、写历史记录、更新统计基础数据 |

## 10. 异常处理设计

系统采用统一异常处理：

| 异常类型 | 处理方式 |
| --- | --- |
| 参数错误 | 返回 400 类业务错误，提示字段原因 |
| 未登录 | 返回未认证错误，前端跳转登录页 |
| 无权限 | 返回权限不足，前端隐藏或禁用对应操作 |
| 状态不允许 | 返回业务异常，例如已派单工单不能撤销 |
| 数据不存在 | 返回资源不存在 |
| 文件上传失败 | 返回上传失败并提示重试 |
| 系统错误 | 记录日志，返回通用错误提示 |

统一响应建议格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

业务失败示例：

```json
{
  "code": 40001,
  "message": "当前工单状态不允许撤销",
  "data": null
}
```

## 11. 部署方案

### 11.1 本地开发部署

本地开发建议：

- 前端使用 Vite dev server。
- 后端使用 Spring Boot 本地启动。
- MySQL 使用本地安装或 Docker 容器。
- Redis 可选。
- 文件上传保存到本地开发目录。

### 11.2 Docker Compose 部署

测试环境建议使用 Docker Compose：

- `frontend`：Nginx 托管前端静态资源。
- `backend`：Spring Boot Jar 镜像。
- `mysql`：数据库容器。
- `redis`：缓存容器，可选。
- `minio`：文件对象存储，可选。

### 11.3 Kubernetes 部署

如果后续需要 K8s 展示，可以拆为：

| 资源 | 说明 |
| --- | --- |
| Deployment/frontend | 前端 Nginx 容器 |
| Deployment/backend | 后端 Spring Boot 容器 |
| Service/frontend | 暴露前端服务 |
| Service/backend | 暴露后端服务 |
| ConfigMap | 保存非敏感配置 |
| Secret | 保存数据库密码等敏感配置 |
| PersistentVolumeClaim | 保存数据库和文件持久化数据 |
| Ingress | 统一入口和路径转发 |

课程实现阶段不强制使用 K8s，Docker Compose 已能满足运行和演示。

## 13. 测试策略

| 测试类型 | 工具 | 重点 |
| --- | --- | --- |
| 单元测试 | JUnit 5 | 状态流转、日期校验、异常规则 |
| Mock 测试 | Mockito | Service 依赖隔离测试 |
| 接口测试 | Postman / Apifox | 登录、报修、留宿、审核接口 |
| 集成测试 | Spring Boot Test | 事务、Mapper、接口链路 |
| 前端测试 | 手工测试为主 | 表单校验、权限菜单、状态展示 |

重点测试场景：

- 报修审核通过、退回、重新提交。
- 自动派单、拒单、超时未处理、异常工单。
- 强制派单后自动接单。
- 维修延期通过、不通过和超时未修好。
- 学生确认、自动确认、重修。
- 留宿日期不在开放区间。
- 留宿时间段重叠。
- 留宿锁定后禁止编辑。
- 留宿待修改重新提交和逾期归档。

## 1. 设计范围

动态结构设计描述学生、宿管、系统管理员、维修人员与系统，在关键用例中的业务交互，以及业务对象允许发生的状态变化。现有图组覆盖账号登录、报修、假期留宿、住宿分配、站内消息和后台运维任务。

- **时序图统一为业务视角。** 生命线只能使用学生、宿管、系统管理员、维修人员和系统；按场景只画实际参与者，不要求每张图都包含全部四类角色。人员使用 `actor`，系统使用 `participant`。
- 四类角色分别表达，不把“宿管/系统管理员”或“四类接收用户”合并成一条生命线。系统是宿舍系统的整体边界，不新增第五个业务角色。
- 角色向系统发送提交、审核、接单、查看、确认等业务动作；系统向角色返回业务结果或通知。自动派单、日期检查、状态更新、归档和后台处理用系统自消息表达。
- 图内不出现操作端、控制器、服务、数据访问对象、数据库、定时器、执行器等独立生命线，不展示接口地址、方法调用、令牌或 SQL。
- `alt` 表示互斥分支，`opt` 表示有条件发生的流程，`loop` 表示按业务条件重复，`par` 表示并行业务活动。后续动作以当时仍符合条件为前提，不能把可选片段理解为必然依次发生。
- 时序图使用状态图中的中文状态名称。工单、派单记录、延期申请等对象即使同名状态也分别注明对象；不以审核结论替代业务对象当前状态。
- 原有 7 张状态图保留，状态名称、迁移条件与业务决定不因本次改写改变。楼栋、宿舍、床位和人员不新增生命周期图；床位占用及住宿待生效阶段仍由住宿关系和日期推导。

## 3. 权限与系统边界

系统在业务时序图中只有一条生命线。身份校验、数据保存、通知、定时处理和后台任务均是系统承担的职责，不拆出代码对象。四类角色各自的操作端由其角色表达，系统管理员仍以现有 `ADMIN` 角色识别，暂不增加独立管理员资料类。

| 角色/主体 | 可执行的相关动作 | 动态设计中的限制 |
| --- | --- | --- |
| 学生 | 登录、编辑本人允许编辑的报修/留宿申请、撤回未派单报修、确认和评价、申请重修、查看本人住宿和消息 | 必须检查主体归属、状态、期限及提交版本；留宿锁定后不能编辑；正式派单后不能撤销报修 |
| 宿管 | 按管辖楼栋审核报修和留宿、异常/延期/重修处置、人工派单、发布管辖范围消息 | 每个请求再次校验有效楼栋范围；不得审核未提交草稿或过期版本 |
| 维修人员 | 查看本人派单、按时接单或拒单、申请延期、提交维修结果 | 拒单必须提供原因；维修和延期只能由当前负责人提交 |
| 系统管理员 | 系统级账号、住宿和批次配置；全校范围的授权管理、人工协调或运维任务 | `ADMIN` 角色表达系统管理员；仍须校验所需系统权限和特殊操作二次确认 |
| 系统 | 身份和业务校验、自动派单、截止锁定、超时处理、自动确认、归档、业务通知及后台任务 | 使用系统自消息表达自动动作；每次执行核对最新业务事实，不重复计数、不覆盖有效人工操作、不冒充操作者 |

系统管理员对学生账号拥有管理权限，不因此自动成为宿管，也不应绕开宿管的楼栋审核规则。业务流程里有宿管审核责任的场景，系统管理员仅在明确的异常处置、补录复核或有对应授权时介入。

## 4. 状态字典与规则

### 4.1 报修工单

| 状态 | 进入条件或含义 | 主要后续 |
| --- | --- | --- |
| `DRAFT` 待编辑 | 新工单草稿，或正式派单前撤回后选择复用 | 提交为待审核、继续编辑或放弃 |
| `PENDING_REVIEW` 待审核 | 学生提交新版本，或创建重修关联工单 | 通过进入待派单；退回进入待修改 |
| `PENDING_EDIT` 待修改 | 宿管不通过并记录原因 | 重交回待审核；期限到后关闭/归档；正式派单前允许撤回 |
| `PENDING_ASSIGN` 待派单 | 审核通过，尚未正式建立自动派单等待 | 普通工单进入自动派单；强制派单；人工池 |
| `PENDING_ACCEPT` 待接单 | 存在一条当前自动派单等待响应 | 接单、拒单、接单超时后重新派单或待人工处理 |
| `ACCEPTED` 已接单 | 自动接单成功或宿管强制派单并自动确认 | 延期、完工、施工超时或待人工处理 |
| `DELAYED` 维修延期 | 延期申请审核中，或延期已通过但维修未完成 | 通过后仍维修；不通过按原期限恢复或进入待人工处理；完工 |
| `REPAIRED` 已维修 | 当前维修人员提交维修结果 | 学生确认、确认期限到时自动确认、确认前重修 |
| `CONFIRMED` 已确认 | 学生明确确认或有效自动确认 | 评价归档或不虚构评价而归档 |
| `PENDING_MANUAL` 待人工处理 | 无合格自动派单人、无新候选人或异常施工超时 | 宿管/授权管理员协调并强制派单，或按审核规则退回 |
| `CLOSED` 已关闭 | 待修改超过重交期限，原业务未完成 | 记录关闭原因并归档，不产生维修确认或评价 |
| `WITHDRAWN` 已撤销 | 学生在正式派单前撤回 | 选择复用同一工单返回草稿，或保留原单历史并另建工单 |
| `ARCHIVED` 已归档 | 业务完成，或已关闭工单完成历史归档 | 历史终态，不删除业务事实 |

**自动派单门槛：**拒单次数 + 超时未接次数不超过 2，且仍有未尝试的合格人员时，允许回流自动派单；超过 2 或候选人耗尽进入待人工处理，但仅次数超过门槛或施工超时时标记异常。无匹配人员或候选人耗尽本身不自动满足异常次数条件。施工超时至少一次即记录异常，解除当前负责人并转入手动派单池，不能回普通自动池。

**撤回语义：**用例基线规定“正式派单前可撤回”，因此待审核、待修改、尚未产生派单的待派单/待人工状态可撤回；已经派过单后，即使派单拒绝、超时并回流，也不能再撤回。保留工单、版本和审核历史；“复用原单”不是删除再新增。

### 4.2 派单记录

- 一条 `DispatchRecord` 表示一次自动尝试或一次人工强制派单。自动记录按 `PENDING -> ACCEPTED/REJECTED/TIMEOUT/CANCELLED` 变化；强制派单生成接单已确认的记录。
- 一张工单可有多条历史记录，但同一时刻只有一条当前有效派单。接单、拒单、超时和人工接管竞争时，以同一工单锁及条件状态更新决定唯一成功方。
- `REJECTED`、`TIMEOUT`、`CANCELLED` 区分拒单、未响应和业务取消，不互相替代，不物理删除。施工超时是维修过程异常；即使结束当前派单，也另有超时异常记录。
- 当前维修负荷按已确认的用例范围统计：待接单、已接单（包括强制派单）、维修延期、已维修待确认、已确认未归档都计入；工单归档后退出。拒单、派单已超时或已作废的记录不再计入当前负荷。

### 4.3 假期留宿申请

- `PENDING_REVIEW` 是已提交但未锁定，学生仍可在期限内修改、重交或撤回；`UNDER_REVIEW` 是已锁定待统一审核；`PENDING_EDIT` 是保存不通过原因后解锁的待修改状态。
- 学生对 `PENDING_EDIT` 的重交生成新版本后立即锁定，状态转 `UNDER_REVIEW`。每个审核轮次记录审核人、结论、原因和重交期限；不覆盖原版本。
- 报修和留宿保存未提交编辑时，退回申请仍保持 `PENDING_EDIT` 和原重交期限；不能通过保存草稿重置期限或绕过逾期处理。已提交未锁定的留宿申请保存编辑时，宿管仍只看到上一份已提交版本。
- 批次开放日期是一个连续区间，每段申请的首尾日期均包含且须完全落在区间内。同一申请日期段互不重叠，包括共享边界日。每名学生每批次只有一张申请主体。
- 正常、逾期补录和人工添加是来源，不是主状态。管理员修改已发布开放区间后，受影响申请须重新校验；待复核期间不能把不符合新区间的旧批准直接算作有效留宿。
- `COMPLETED` 只在最后一个已通过日期段结束次日 0 点、并不存在未决开放区间复核时生成。待修改逾期归档表示未按期提交，不生成已完成留宿事实。
- 未提交的纯草稿不计入正式申请统计。任何“取消锁定”或“例外受理”都必须明确授权并保留操作记录。

### 4.4 住宿分配

- 住宿关系的有效区间约定为 `[入住日期, 退宿日期)`；空退宿日期表示持续生效。此半开区间是数据库校验规则，实施前应确认与学校住宿日期口径一致。
- “待生效”由入住日期尚未到达推导，不新增 `PLANNED` 持久状态字段。建立分配时按整个目标区间校验床位和学生冲突，未来分配同样占用该日期段。
- 同一学生的分配资源与涉及的床位按稳定顺序锁定；调宿在同一事务内结束旧区间并创建新区间。退宿保留历史。占用情况由分配推导，`Bed` 只保存可用、维修、停用等管理状态。

### 4.5 延期、消息及系统任务

- 延期申请的状态与工单的 `DELAYED` 并行：审核期间暂停施工超时判断且保留原负责人；批准后按批准的新预计时间计时；拒绝后恢复原期限，若原期限已到则立即按施工超时规则处理。
- 消息主体状态与接收记录的已读状态相互独立。每条 `MessageTarget` 在全体、角色、楼栋、指定账号等类型中取一种；一条消息可有多条目标。所有目标展开后去重，每条消息与每个接收用户最多一条接收记录。已读按接收用户隔离并幂等。
- `ImportExportTask` 与 `BackupTask` 是 ER 分析中两个独立实体，不是一个统一任务实体。`WAITING -> RUNNING -> SUCCESS/PARTIAL/FAILED`；`PARTIAL` 仅用于逐行导入。当前仅定义启动前取消，不假设运行中止能安全回滚。
- 导入逐行校验，保存合法行和错误明细，当前建议部分成功。由实现方决定整批原子或分批提交，不能把“部分成功”写成未执行。导出、备份不上传输入文件；导入、恢复需要上传文件；恢复需要管理员二次确认和维护锁。
- 恢复应在当前备份之外保留恢复任务、确认和审计信息。执行前校验文件、版本、恢复范围和维护条件；创建恢复前保护备份。失败时记录恢复结果及回退结果，回退失败应保持维护状态并提示管理员，不应声称成功。

## 5. 状态与静态设计基线的对应

报修计时默认值沿用 UC-R11，业务时序图统一称为接单截止时间、维修截止时间、确认期限和重交期限；这些期限可配置，不把固定天数写成状态名称：

| 计时事件 | 当前默认值 | 起算/结束规则 |
| --- | --- | --- |
| 自动派单未接单 | 2 小时 | 从该次自动派单发出起计；强制派单不计接单超时 |
| 普通维修未完成 | 24 小时 | 从接单时起计；延期审核期间暂停判定，通过后用批准时间 |
| 紧急维修未完成 | 6 小时 | 从强制派单确认接单起计；超时解除原负责人并转人工池 |
| 已维修未确认 | 7 天 | 从维修结果提交起计；执行前再检查仍未确认 |
| 待修改未重交 | 7 天 | 从审核退回起计；仅保存编辑不重置期限 |

留宿申请和本轮重交期限由对应楼栋规则/审核记录提供；完成归档使用学校业务时区的结束日期次日 0:00，而不是服务器默认时区。配置改变是否追溯在途工单应另行确定，本图不默认回溯改写历史期限。

动态设计优先遵循当前用例说明和用户确认的业务规则。类图中的英文枚举是早期类模型，含义对应关系如下；实现时应统一枚举，避免同时保留两套语义：

| 当前动态语义 | 早期类图/ ER 候选值 | 决策 |
| --- | --- | --- |
| 待编辑 | `DRAFT` | 一致 |
| 待审核 | `PENDING_AUDIT` 或 `PENDING_REVIEW` | 统一命名为 `PENDING_REVIEW` |
| 待修改 | `PENDING_EDIT` | “REJECTED/已驳回”只作为审核结论，不是当前工单状态 |
| 待派单 | `PENDING_DISPATCH` 或 `PENDING_ASSIGN` | 统一命名为 `PENDING_ASSIGN` |
| 待接单 | 早期 `DISPATCHED` / 派单记录 `WAITING` | 建议工单状态 `PENDING_ACCEPT`，派单记录 `PENDING`（对齐早期 `WAITING`） |
| 已接单 | `IN_PROGRESS` | 应改为 `ACCEPTED`；真实开始施工时间可另行记录，不与是否接单混淆 |
| 维修延期 | 早期主状态无独立名称 | 当前工单状态 `DELAYED`，与延期申请审核结论分开 |
| 已维修 | `PENDING_CONFIRM` | 当前动态设计统一为 `REPAIRED`，表示已经完工但尚未确认；早期值仅作含义对照 |
| 已确认 | `CONFIRMED` | 一致；确认方式和时间存维修确认记录 |
| 待人工处理 | 早期主状态无独立枚举 | 补 `PENDING_MANUAL`，不以 `ABNORMAL` 代替 |
| 已关闭 | `CLOSED` | 用于待修改逾期关闭，之后可以归档 |
| 已撤销 | 早期主状态无独立枚举 | 补 `WITHDRAWN`，学生正式派单前撤回 |
| 已归档 | `ARCHIVED` | 一致；不是物理删除 |

派单早期类图 `DispatchStatus` 为 `WAITING/ACCEPTED/REJECTED/TIMEOUT/CANCELLED`；图中采用业务清晰的 `PENDING/ACCEPTED/REJECTED/TIMEOUT/CANCELLED`，分别对应待接单、已接单、已拒单、超时未接、已作废。延期申请当前类图未细列其状态枚举，动态图建议增加过程状态语义，数据库阶段再确认是否以申请记录生命周期/审核结论分开表达。系统任务沿用导入错误明细和独立的导入导出/备份实体，不合并 ER 实体。

## 6. 业务结果与操作一致性

### 6.1 时序图与状态图对照

| 业务事件 | 对应状态变化 | 时序图 / 状态图编号 |
| --- | --- | --- |
| 报修提交、审核及退回重交 | 待编辑或待修改 -> 待审核；通过 -> 待派单；不通过 -> 待修改 | 02 / 08 |
| 正式派单前撤回、复用 | 可撤回状态 -> 已撤销；复用 -> 待编辑；曾正式派单则拒绝撤回 | 02 / 08 |
| 自动派单及人员响应 | 工单待派单 -> 待接单 -> 已接单，或回待派单 / 待人工处理；派单记录分别为待接单、已接单、已拒单、超时未接 | 03 / 08、09 |
| 强制派单、人工协调和施工超时 | 强制派单直接为已接单；协调后按条件回自动池、留人工池或退回待修改；施工超时 -> 待人工处理且标记异常、作废旧派单 | 03 / 08、09 |
| 延期申请、审核及失效 | 工单已接单 -> 维修延期；申请为待审核 -> 已通过 / 未通过 / 已失效；驳回按原期限回已接单或待人工处理 | 12 / 08、14 |
| 完工、确认、评价及重修 | 已接单或维修延期 -> 已维修 -> 已确认 -> 已归档；重修保留原单为已维修，关联新单从待审核开始 | 03、17 / 08、09、14 |
| 留宿提交、锁定、审核和重交 | 待编辑 -> 待审核 -> 审核中 -> 已通过或待修改；待修改重交立即为审核中；合法取消锁定回待审核 | 04 / 10 |
| 留宿区间复核与补录 | 复核通过保持已通过，退回为待修改；特殊受理新提交版本立即锁定为审核中，来源不是新状态 | 13 / 10 |

| 住宿安排、调宿、退宿及取消 | 未来分配待生效，到期有效；调宿或退宿时旧关系结束；生效前合法撤销为已取消 | 05 / 11 |

表中状态均指明所属业务对象。报修的“已驳回”和留宿的“驳回”是审核结论，主状态仍为待修改；异常、紧急、重修和申请来源均不替代主状态。未明确的重修计时和无评价归档规则继续列为待确认。

### 6.2 共同约束

1. **结果完整：** 提交内容与状态、审核结论与状态、延期结论与维修期限、完工结果与已维修、确认事实与已确认、评价与归档、调宿的新旧关系必须共同生效；失败时不得留下只有一半的业务结果。
2. **以最新事实为准：** 接单与超时、完工与延期审核、重交与逾期归档、撤回与审核同时发生时，系统再次核对当前状态、内容、负责人和期限，只接受仍合法的操作。
3. **重复操作不重复产生事实：** 重复提交、接单、确认、评价、任务执行及通知补发不得重复生成记录。一次接单超时或施工超时只计算一次。
4. **通知对应真实结果：** 状态变化成功后才通知对应人员。通知失败须留有可补发信息；补发不重复生成同消息同用户的接收记录。
5. **住宿不重复占用：** 同床位同日期区间只能有一名学生；同学生同日期区间只能有一个有效住宿关系。未来住宿同样参与区间检查，调宿的新旧区间必须正确衔接。
6. **操作和消息按归属隔离：** 每次操作核对本人、角色、楼栋或全校范围。管理员查看全校业务的权限不等于可以修改其他用户的个人已读状态。
7. **任务受理与完成分开：** 创建待执行任务只表示已受理。只有实际处理和校验通过才为成功；取消仅在未启动时成立，执行与取消不能同时生效。
8. **历史可追溯：** 登录结果、审核理由、实际录入人、派单尝试、超时、确认方式、归档原因及任务结果均保留必要记录；恢复数据不得覆盖本次恢复任务和审计事实。

## 7. 与业务资料的差异及处理

1. [UC-R01 和当前用例基线](../用例设计/00%20用例说明与设计约定.md) 规定只有正式派单前允许学生撤回；旧活动图中曾写“学生可撤回”，本动态设计不把已派单后撤回纳入流程。
2. 自动派单按用例阈值 `拒单次数 + 超时未处理次数 <= 2` 且仍有候选人才可自动回流；超过门槛、候选人耗尽或施工超时进入待人工处理。仅非异常普通工单在协调出合格新候选人后可以回自动池；异常、紧急和重修工单仍只进手动池，与状态图一致。
3. 旧维修流程图提到“待修改超时自动确认”。这与“确认维修”必须有完工记录的语义冲突。当前设计按 `PENDING_EDIT -> CLOSED -> ARCHIVED` 处理，不产生伪造维修确认，也不生成评价。
4. 旧流程图将延期申请并入工单的一个状态分支。当前将工单 `DELAYED` 与独立的延期申请状态并行表达，避免审核中、已批准混成一种事实。
5. 维修人员曾以 `IN_PROGRESS` 表达已接单。为对齐待维修计时、延期和接单概念，动态状态使用 `ACCEPTED`；是否增加独立 `IN_PROGRESS` 页面状态不在当前用例基线内。
6. 住宿分配图按时间区间定义床位/学生冲突，并不从 `Bed` 中另存占用值；请在数据库方案里实现等效的事务与区间冲突保证。
7. 备份图给出上传、导出、备份、恢复的不同输入条件；恢复的实际停服/维护策略取决于部署环境，不表示当前技术栈已经选定该能力。

## 8. 待业务确认的规则

以下内容当前资料没有给出足够规则。图稿明确标记为待定或采用最小推断，进入详细开发前应确认：

1. **重修与原工单自动确认：** 是否学生提交重修后暂停原已维修工单的自动确认计时。当前按用例仅允许“自动确认前申请重修”，不擅自把重修申请当作暂停事件。
2. **自动确认后归档及评价：** 用例一处说超时后自动确认并归档，另一处又把评价作为归档前操作。当前将确认和评价分开，允许按配置归档且不伪造学生评价；确认自动归档时限需明确。
3. **待修改超期：** 报修业务指定 7 天自动关闭；业务图另有待修改超时自动确认表述。当前遵循用例设定的关闭并归档语义。
4. **区间修改影响已通过申请：** 当前采用重新校验、宿管复核，不符合时退回待修改并停止计入有效留宿。需要业务方确认历史有效性、已生效申请及学生通知口径。
5. **单独取消留宿锁定：** 截止前提前锁定后何时可解锁、截止后何种例外可以解锁，须有权限和审计规则；当前只把经授权的解锁作为例外转换。
6. **非本人录入特殊留宿申请：** 记录真实录入人及学生来源。管理员的复核责任是否与宿管的楼栋审核形成双人双审、哪类申请需要二审，仍需确定。
7. **住宿日期边界：** 当前建议 `[入住日, 退宿日)`。如现行业务把退宿日也视作占用日，需要统一公式和数据库冲突检查。
8. **无评价自动归档：** 确认后逾期未评价是否自动归档、期限几天，需确认；不能用无评价伪造评分或评价记录。
9. **恢复任务可靠性：** 维护锁、应用停写、附件回退、恢复记录在目标数据库被覆盖后的保存方式，须按实际部署和备份工具确认。
10. **导入提交策略：** 当前建议逐行处理并显式报告部分成功。是否要求全批回滚需由各数据类型业务规则确认。
11. **取消未来调宿：** 状态图允许待生效分配取消。取消关联调宿时如何恢复旧关系的退出日期、如何处理其他后续安排，仍需明确；图中只在关联安排妥善处理后执行取消，不预设无条件恢复。
